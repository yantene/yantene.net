# ADR (Architecture Decision Records)

アーキテクチャ的に重要な決定は ADR として `docs/adr/` に記録する。
導入の経緯は [docs/adr/0001](../../docs/adr/0001-record-architecture-decisions.md)、
一覧は [docs/adr/README.md](../../docs/adr/README.md)。

## いつ書くか

後で「なぜ？」と問われる決定、覆すのが高コストな決定、横断的な決定を記録する。例:
コンテンツ正本の置き場所、永続化・スキーマ方針、レイヤー構成、外部サービス選定、
セキュリティヘッダーの方針、重要なトレードオフ。些末な実装詳細やリバート容易な変更は対象外。

## 何を書くか

ADR は**いま、この設計がどうなっていて、なぜそうなのか**を書く。読んだ人が現在の
コードベースを理解するために必要なことだけを残す。次のものは書かない。

- 廃案になった選択肢の変遷 (「かつては X だったが Y に移った」)。今の姿だけを書く
- まだ実装されていない将来計画 (「いずれ Z へ移行する」)。実装したときに書く

「検討した選択肢」に並べるのは、**今の設計を選んだ理由を説明するために要る対案**であって、
過去に採用して捨てた実装の記録ではない。

## どう書くか

- フォーマットは MADR 短縮版。`docs/adr/template.md` を雛形にコピーする。
- ファイル名は `NNNN-kebab-title.md` (4 桁連番 + 意図を表すタイトル)。連番は既存の最大 +1。
  欠番は統合のときだけ生まれる (下記)。`scripts/check-adr.mjs` が CI で連番の重複・
  命名規則・参照の行き先を検査する。
- Status は `Proposed → Accepted → Deprecated` で遷移させる。
- アーキ的に重要な変更を含む PR では、対応する ADR の追加/更新を行う。

## 不変性 (immutable)

**不変性は「決定の履歴」ではなく「現在の設計の説明」を守るためにある。**

原則として、Accepted になった ADR の本文は書き換えない。決定が変わったら新しい ADR を
起こし、旧 ADR の Status を `Deprecated` にして新しい ADR へリンクする。

### ただし、割れた主題は統合してよい

上の原則を守り続けると、同じ主題の ADR が増え、**1 つのことを知るのに何本も読ませる**
状態になる。それは ADR の目的 (いまの設計とその理由が分かること) に反する。

**同じ主題が 3 本以上に割れたら、統合してよい。** 判断の目安は Status 欄で、
「〜のみ 00NN で置き換え」のような但し書きが付き始めたら候補になる。

統合するときの決まり。

- **吸収する側は、番号の小さいほう** (最初にその主題を決めた ADR)
- **番号は振り直さない。欠番を残す。** リポジトリの外 (コミットメッセージ・マージ済み
  PR・Issue) に残る参照が行き先を失うため
- **`docs/adr/README.md` の「統合した番号」表に旧番号と行き先を書く。**
  `scripts/check-adr.mjs` がこの表を読み、消えた番号を指す参照が残っていないかを検査する
- **統合後の本文には経緯を残さない。** 「かつては X だったが Y に移った」は書かず、
  いまの姿だけを書く (この文書の「何を書くか」に従う)
