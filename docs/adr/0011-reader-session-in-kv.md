# 0011. 読み手のセッションを KV に置き、同じ日の読み直しを数えない

- Status: Accepted
- Date: 2026-08-12
- Deciders: @yantene

## Context / 背景

ノートの閲覧は、開かれるたびに累計 (`view_count`) と人気の目安 (`view_log_score`) を
押し上げる。押し上げる重みは新しいアクセスほど大きい (domain/note-view/view-ranking)。

そのため、同じ人が同じ記事を開き直すだけで順位が動く。書いた本人が推敲のたびに開く、
読者がリロードする、一覧と記事を行き来する — どれも一人の関心でしかないのに、
「よく読まれている記事」がそれを反映してしまう。母数が小さいうちほど効く。

読み直しを外すには「誰が何を読んだか」を突き合わせる必要がある。加えて、読み手ごとの
状態を要求する機能は閲覧数だけではない。ノートへの emoji reaction を一人 1 つに
限るのにも、同じ「この人が何をしたか」が要る。個別に仕組みを作らず、読み手ひとりぶんの
状態をまとめて置ける場所を 1 つ用意する。

## 検討した選択肢

- **案 A: 読み手に預けた cookie だけで判定する** — 「今日読んだ記事」を cookie の値に
  持たせ、サーバーは受け取った値をその場で見るだけにする。
  - Pros: サーバーに記録が増えない。読み手を指す識別子も発行しない。ストレージも
    掃除の運用も要らない。
  - Cons: 値の上限 (4096 バイト) に縛られ、持てる状態が「今日ぶん」程度で尽きる。
    読み手が中身を書き換えられるので、reaction のように「もう押した」を守りたい
    ものは載せられない。
- **案 B: セッションを KV に置く** — 推測できない識別子を発行して cookie に預け、
  状態そのものは KV に持つ。
  - Pros: 状態の大きさに実質制限がなく、読み手が書き換えられない。閲覧の重複排除も
    reaction の重複防止も同じ場所に載る。期限は KV が自動で切るので掃除が要らない。
  - Cons: 読み手を辿れる記録がサーバーに残る。閲覧のたびに KV の読み書きが増える。
- **案 C: セッションを D1 に置く** — 同じことを既存の D1 で行う。
  - Pros: 新しいバインディングが要らない。強い整合性が得られる。
  - Cons: 読み手ごとの行が、ノートのメタデータインデックスと同じ DB に混ざる。
    期限切れの掃除を自分で回す必要がある。1 閲覧ごとの書き込みが D1 に乗る。

## 決定

**案 B を採る。** 128 bit の乱数を識別子として発行し、`session` cookie に預ける。
状態は KV (`SESSIONS` バインディング) の `session:<id>` に置く。

KV を選んだのは、読み手ごとの状態が「識別子で引いて丸ごと書き戻す」形にきれいに
収まり、期限切れの掃除を自前で持たなくてよいため。整合性は結果整合だが、置くのが
順位の目安である以上、まれな取りこぼしは順位が少しぶれるだけで済む。

セッションが持つのは、いまのところ発行日と「その日どのノートを数えたか」だけ。
日が変われば前日ぶんは捨てる。溜め続けると読み手の閲覧履歴そのものを持つことになり、
順位を出すのに要らないものを抱えることになるため。

識別子は**推測できないことが要件**。当てられると他人のセッションになりすませるので、
連番や時刻由来ではなく乱数を使う (`SessionId.issue`)。cookie の値の検証は形しか
見ておらず、なりすましを防いでいるのは乱数の広さだけである。

セッションを起こすのは人が読んだときだけで、クローラーには発行しない。

cookie の作りは以下のとおり。

| 項目     | 値                       | 理由                                                                   |
| -------- | ------------------------ | ---------------------------------------------------------------------- |
| 値       | 識別子のみ (22 文字)     | 意味のある値は KV 側にある。これはそこを指す鍵                         |
| Max-Age  | 400 日 (保存のたび延長)  | ブラウザが cookie に許す上限。読み続けている人のセッションを切らさない |
| Path     | `/`                      | セッションはノートに限った話ではない                                   |
| HttpOnly | 付ける                   | 鍵を読み手の JavaScript に触らせない                                   |
| SameSite | `Lax`                    | 他所のリンクから来た人も同じ人として扱う                               |
| Secure   | development 以外で付ける | CSP と同じ切り分け ([0007](0007-strict-csp-outside-development.md))    |

KV レコードの期限も同じ 400 日で、書き込みのたびに引き直す。cookie と KV で寿命を
揃えるのは、「ブラウザには残っているのに記録が無い」状態を作らないため。

読めない記録は throw せず「無い」とみなす。そのまま失敗させると、その読み手は期限が
切れるまで何も数えられなくなる。同じ識別子のまま起こし直せば、次の保存で上書きされて
直る。ただし一部だけ読める記録も丸ごと捨てる。中途半端に生き残らせると、壊れたものが
「正しい記録」として書き戻されてしまう。

書く順は、セッション → D1 の数。途中で落ちたときに数え過ぎより数え落としを選ぶため。
逆順にすると、書き込みに失敗した回だけ何度でも数えられ、この ADR の目的そのものが崩れる。

## 帰結 / Consequences

- 良い面: 読み手ごとの状態を置く場所ができ、閲覧の重複排除も、これから足す
  reaction の重複防止も同じ仕組みに乗る。期限切れは KV が自動で捨てる。
- 悪い面・トレードオフ:
  - **読み手を辿れる識別子をサーバーが持つことになった。** 名前も IP も持たないが、
    「同じブラウザから来た人」は辿れる。セッションに置くのは辿られて困らないものだけに
    留めること。cookie の同意が要る種類のものではないが、以前のように「サーバーは
    回数しか知らない」とは言えなくなった。
  - 閲覧のたびに KV の読み取りが 1 回、その日の初回には書き込みが 1 回増える。KV の
    無料枠は書き込み 1000/日なので、読者が増えれば有料プランが要る。
  - KV は結果整合で、同じキーへの書き込みは 1 秒に 1 回まで。連続で開かれると
    まれに取りこぼし、その回は数え直す。
  - cookie を消す・切っている相手、別のブラウザから来た相手は別人として数える。
  - ノートのページ応答に `Set-Cookie` が乗る。HTML を共有キャッシュに載せるなら、
    読み手をまたいで cookie が配られないことを確かめる必要がある (現状 HTML は
    キャッシュしていない)。
- 検証方法 / 今後の宣言: `session.entity.test.ts` が日跨ぎと重複の扱いを、
  `session-id.vo.test.ts` が識別子の形と重複しないことを、`session-cookie.test.ts` が
  cookie の属性と読み戻しを、`session.repository.test.ts` が KV との往復と壊れた
  記録の扱いを固定する。
