# 0024. 時計の開き位置を SSR で決め、JST の実時刻と実際の月齢から始める

- Status: Accepted
- Date: 2026-08-15
- Deciders: @yantene

## Context / 背景

トップページの時計 ([0008](0008-interactive-day-clock-via-web-animations-api.md)) は、
CSS アニメーションの `currentTime` 0 から始まる。位相 0 は南中で、月齢は満月に固定して
あった。開くたびに同じ絵になるのを避けるため、描画がついた後に JS が位相を乱数でずらして
いた。

これは直せない位置に置かれていた。SSR した HTML はハイドレーションより先に描かれるので、
**南中の空が必ず一度描かれてから乱数の位置へ飛ぶ。** `useLayoutEffect` に変えても、
ブラウザが最初のフレームを描くのは JS が動くより前なので変わらない。開始位置は SSR の
時点で決まっていなければならない。

決まっていなければならない値は 2 つある。時刻 (1 日の中のどこか) と月齢 (朔望月の中の
どこか) で、どちらも連続量である。ところが「見た目の可変軸は静的な CSS のクラスの段階で
持つ」という規律がある。`style-src` は数式のために緩めたが
([0019](0019-inline-style-for-math.md))、規律のほうは lint (`react/forbid-dom-props`) で
明示的に残してある。

## 検討した選択肢

- **案 A: 空を隠しておき、ハイドレーション後に見せる** — ヒーローを不可視で描き、JS が
  位相を決めてから表示する。
  - Pros: いまの実装をほとんど変えずに済む。
  - Cons: JS が無い環境で空が永久に出ない。プログレッシブエンハンスメントを捨てることに
    なり、0008 が守った性質を壊す。
- **案 B: SSR した HTML に inline style で連続値を渡す** — `--clock-shift` を style 属性で
  与える。
  - Pros: 5 行で済み、刻みが要らない。CSP はもう落とさない (0019)。
  - Cons: 0019 が意図して残した規律を破る。#78 と #80 で実際に壊れた書き方でもある。
- **案 C: 段階クラスを SSR で選ぶ (採用)** — 時・分・月齢を CSS クラスの列挙として持ち、
  loader が選んだものを HTML に載せる。
  - Pros: 規律のまま。最初のフレームから正しい絵が出る。JS が無くても効く。
  - Cons: 機械的な CSS ルールが 64 本増える。刻みが TS と CSS の 2 か所に散る。

あわせて、乱数のままにするか実時刻にするかも決めた。乱数には「開くたびに違う」以外の
意味がなく、月齢を実物に合わせれば日食が実際に起きた日に日食が出る。

## 決定

案 C を採る。開始位置は loader が決め、`clock-origin.css` の段階クラスとして HTML に
載せる。位置の決め方は乱数ではなく実時刻とする。

- 時刻は `Asia/Tokyo` 決め打ちで読む。`request.cf.timezone` から読者のローカル時刻に
  合わせる手もあるが、そうすると HTML が読者の地理に依存し、共有キャッシュに載せられなく
  なる。空の色は装飾なので、筆者の時間帯で足りる
- 月齢は実際の朔から求める。平均朔望月だけでは最大 0.6 日ずれ、日食の日に日食が出ない。
  Meeus の朔望計算の主要な補正項を入れて分単位で合わせ、既知の日食 3 つで固定した
- 刻みは時刻が 5 分、月齢が 1 日。1 日を 288 秒で回しているので、実時間の 1 秒が世界内の
  5 分にあたる。ページが描き終わる頃には 5 分ぶん進んでおり、これより細かくしても意味がない
- 位相をずらすのは 1 つの量だけにする。時計に属する 9 本のアニメーションすべてに、同じ
  絶対時間を `animation-delay` として足す。0008 が「全部に同じ増分を与える」と決めたのと
  同じ理屈を、連続値ではなく静的な値でやっている

### 守るべき不変条件が 2 つある

**ずらし量は必ず負でなければならない。** 正の `animation-delay` は「まだ始まっていない」を
意味し、`fill-mode` が none なのでその間はキーフレームが一切当たらない。空は背景色を失って
透け、太陽は止まったままになる。南中より前の時刻をそのまま書くと正の値になるため、代わりに
翌日の同じ時刻まで進める。空も太陽も目盛りも周期がちょうど 1 日なので、進めても絵は変わら
ない。

**月齢に端数を入れてはいけない。** 月齢は月の 2 つのアニメーション (公転・位相) にだけ効き、
空と太陽には効かない。整数日なら太陽の側が 1 日周期でちょうど元に戻るので「時計全体を N 日
進めた」のと同じ絵になるが、端数を入れると太陽だけが取り残され、月の位置が離角と食い違う
(0.25 日で 90 度)。月相のほうは正しく出るので、満ち欠けと位置が噛み合わない月が静かに
出来上がる。1 日より細かい月齢は時刻のずらしが占めていて動かせないため、画面に出る月齢は
実際の月齢から最大で半日ずれる。

## 帰結 / Consequences

- 良い面:
  - 最初のフレームから正しい空が出る。乱数でずらす JS (`randomizeDayClock`) と、描画後に
    読み上げ用の時刻を合わせ直す `requestAnimationFrame` が丸ごと消えた。
  - `prefers-reduced-motion` で止めている読者にも時刻が届く。以前は必ず南中で固まっていた。
  - 月の位置と満ち欠けが実物と揃う。満月の夜は月が空に出ていて、朔の日は太陽に重なる。
- 悪い面・トレードオフ:
  - 刻みが `clock-origin.ts` の定数と `clock-origin.css` のルールに分かれて存在する。
    片方だけ変えると、当たらないクラスが HTML に載り、空が南中のまま出る。
  - 現実と一致するのは開いた瞬間だけで、288 秒後には 1 日ぶん進んでいる。
  - 開始位置が時刻に依存するため、**トップページの HTML を共有キャッシュに載せられない。**
    いまドキュメントに `Cache-Control` は付いておらず、Service Worker はページを
    network-first で扱う ([0010](0010-hand-written-service-worker-without-precache.md)) ので
    問題は出ないが、後からキャッシュを足すときはここを見直すこと。
- 検証方法 / 今後の宣言:
  - `clock-origin.test.ts` が、既知の日食 3 つで月齢の計算を固定し、載せるクラスがすべて
    `clock-origin.css` に実在することを 1 日ぶんと朔望月ぶんの時刻で確かめる。
  - CSS の噛み合わせはブラウザでしか確かめられない。実装時は開発サーバーで、(1) 正の
    `animation-delay` を持つ時計アニメーションが 1 本も無いこと、(2) 目盛りの位相から
    逆算した時刻が JST と一致すること、(3) 月相アニメーションの進捗と太陽・月の公転盤の
    角度差が同じ月齢を指すことを見る。この 3 つはいずれも、見た目だけでは気づけない。
  - CSP を有効にした確認は `pnpm run preview:staging` で行う
    ([0007](0007-strict-csp-outside-development.md))。
