# 0029. タグをやめ、分類は `article` の 1 つに畳む

- Status: Accepted
- Date: 2026-09-01
- Deciders: @yantene

## Context / 背景

記事にはフロントマターでタグを付けていた。用途は 2 つで、関連ノートの並べ替えと、
一覧の絞り込み (`/notes?tag=<タグ>`) である。

前者は [ADR 0028](0028-relate-notes-by-embedding-similarity.md) で本文のベクトルに
置き換えた。タグを使わずに並ぶようになったので、タグに残った仕事は絞り込みだけになる。

その絞り込みも働いていない。55 本でタグは延べ 113 個・19 種類しかなく、34 本に「日記」が
付いている一方、1 記事にしか付いていないタグが 9 種類ある。粗すぎる分類と細かすぎる分類が
同居していて、どちらの側からも記事を探せない。記事を探す手段としては全文検索
(`notes_fts`) が別にあり、そちらは語彙が一致すれば必ず引ける。

そして書き手にとっては、記事を 1 本書くたびに「どのタグを付けるか」を決める手間が残る。
その判断は読み手の役に立っておらず、続ける理由が無い。

## 検討した選択肢

- **案 A: 全部やめる (採用)** — 書かない・出さない・持たない。
  - Pros: 書き手の手間が消える。分類の経路が 1 つ減り、記事を探す手段が全文検索に一本化される
  - Cons: 外向きの表現 (Atom の category、microformats2 の p-category) が失われる
- **案 B: 表示だけやめる** — UI から外し、フロントマターと D1 には残す。
  - Pros: 戻しやすい
  - Cons: 書き手の手間が残る。廃止の目的を果たさない。見えないデータが残り、
    後から見た人に「なぜ持っているのか」が説明できない
- **案 C: 絞り込みだけ残す** — タグ索引と記事のタグ表示を消し、`?tag=` は残す。
  - Cons: 入り口の無い機能になる。書き手の手間も残る

## 決定

案 A を採る。タグの露出面をすべて落とす。

- 一覧の絞り込み `?tag=` — ページ・JSON API・Atom の 3 経路すべて。**404 にはせず、
  クエリを無視して全体を返す。** 購読中のリーダーに「消えたフィード」と扱わせないため
- タグ索引 (`/notes` に出していたもの)、記事と一覧のタグ表示
- 公開 JSON API `/api/v1/tags`
- JSON-LD の `keywords`、OG 画像に描いていたタグ行
- フロントマターの `tags` を refresh が読まない。`NoteTag` VO も落とす

`note_tags` の表そのものは、コードから落とすのと同じリリースでは落とせない。デプロイは
migration を当ててから走るので、drop する migration と、その表を読まなくしたコードを
1 つのリリースに入れると、`Migrate D1` が先に走った数十秒のあいだ旧コードが消えた表を
読む (environments.md)。**読まなくなったコードを先に出し (v2026.09.01.1)、drop は次の
リリースに回した (migration 0010)。**

旧サイトから来る `/list.html?tag=<タグ>` は、tag を捨てて `/notes` へ丸める。飛んだ先が
空にならず、外部に残ったリンクも死なない。

### 分類は `article` の 1 つだけ残す

タグは無くなるが、**「これは記事である」という自己記述は残す**。microformats2 の
`p-category` と Atom の `<category term>` に、記事ごとに変わらない `article` を出す。

`article` を選んだのは、[Post Type Discovery](https://www.w3.org/TR/post-type-discovery/)
が `p-name` と `e-content` から導く型と一致するため。記事ページの `h-entry` は
`p-name` (表題) を持ち、その値は `e-content` の先頭部分ではないので、この記事は
`article` と判定される。同じ語をカテゴリにも使えば、受け手から見て型とカテゴリが
食い違わない。

サイトの呼び名である `note` は採らない。Post Type Discovery の `note` は「タイトルの
無い短い投稿」を指す語で、この記事群とは逆の意味になる。内部の呼び名と外向きの語彙が
食い違うときは、外向きの語彙に合わせる。

全記事に同じ値が付くので、購読者のフィルタとしては機能しない。**それは承知の上で、
自己記述としてだけ置く。**

## 帰結 / Consequences

- 良い面: 記事を書くときにタグを決めなくてよい
- 良い面: 記事を探す経路が全文検索に一本化される。「タグで探す」と「語で探す」の
  どちらで引けるのかを読み手が考えなくてよくなる
- 悪い面: タグでまとめて読む手段が無くなる。「日記だけ読む」ができない
- 悪い面: `?tag=` を含む外部リンクは、絞り込みの効かない一覧に着く。404 よりはよいが、
  リンクを張った人の意図どおりには動かない
- トレードオフ: 分類を完全に無くさず `article` を 1 つ残すのは、mf2 と Atom で
  「分類が無い」と読まれるのを避けるため。情報量はゼロだが、機械が読む面での欠落にはしない
- 悪い面: 2 つのリリースのあいだ、誰も読まない表が残った。記事を消したときの掃除も
  外していたのでその行は溜まったが、表ごと落としたので片付いた
- 検証方法: `feed.handler.test.ts` が Atom に `article` のカテゴリが出ることと、
  `?tag=` を付けても全体が 200 で返ることを固定する。`note-header.mf2.test.tsx` が
  `p-category` に `article` が出ることを、`pages.handler.test.ts` が `?tag=` を無視して
  全件返すことを固定する
