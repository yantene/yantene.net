# 0041. プロフィールをコンテンツリポジトリに置き、記事と同じ経路で同期する

- Status: Accepted
- Date: 2026-09-13
- Deciders: @yantene

## Context / 背景

サイトは 3 か所で同じ「書き手が何者か」を出す。

| 場所       | 出すもの                                                        |
| ---------- | --------------------------------------------------------------- |
| トップ     | 短い自己紹介と、代表 h-card (名前・顔・出ていく先)              |
| 記事の末尾 | 筆者紹介。顔・名前・短い自己紹介・出ていく先・`/about` への導線 |
| `/about`   | 全部。長い自己紹介                                              |

これまで自己紹介は `hero-section.tsx` に 3 行の直書きで、`/about` は中身が無かった。
書き換えるたびにコードを直してデプロイすることになり、**記事は push で直せるのに自分の
紹介文は直せない**という非対称があった。

同時に、この 3 か所は同じものを出すのだから 1 つのデータから賄いたい。写すと、必ず
どれかが古びる。

## 検討した選択肢

- **案 A: コードに直書きし続ける** — いまの姿。
  - Pros: 何も作らなくてよい。
  - Cons: 文面の修正がデプロイを要する。3 か所に写すことになる。
- **案 B: 管理画面を作る** — D1 を直に編集する画面を置く。
  - Pros: 書き換えが早い。
  - Cons: product.md が「管理画面は設けない」と決めている。認証・入力検証・履歴の
    どれもが新しい面になる。**書いたものの原本がどこにも残らない**。
- **案 C: コンテンツリポジトリに置き、記事と同じ経路で同期する** — `profile.md` + `profile/`。
  - Pros: 書き換えが push で済む。原本が git に残る。記事の同期の仕組みをそのまま使える。
  - Cons: 同期の経路が 1 本増える。D1 に表が 2 つ増える。

## 決定

**案 C。** コンテンツリポジトリに `profile.md` と `profile/` を置き、push を合図に D1 と R2 へ同期する
([ADR 0034](0034-artifacts-as-content-source-of-truth.md) /
[ADR 0035](0035-refresh-on-push-through-a-queue.md))。記事 (`articles/<slug>.md` +
`articles/<slug>/`) と同じ対の形なので、変更検出・書き込みの順・掃除の決めをそのまま写せる。

**短い自己紹介と長い自己紹介を分けて持つ。** 短いほうはフロントマターの 1 欄、長いほうは
本文 (Markdown)。記事の末尾は記事を開くたびに短いほうを読むので、長文まで運ぶ理由が無い。
長い自己紹介を読むのは `/about` だけになる。

保存先は記事と同じ分担にする。

| 置き場 | 持つもの                                                |
| ------ | ------------------------------------------------------- |
| D1     | 名前・短い自己紹介・顔の URL・出ていく先・`source_hash` |
| R2     | 長い自己紹介の原文と MDAST、顔写真などのアセット        |

D1 に持つのは、記事の末尾が毎回読むため。R2 の MDAST を毎回読んで先頭を切り出す形にすると、
記事を 1 本開くたびに本文まるごとを読むことになる。

**プロフィールは常に 1 行**なので、`profile` 表の主キーは固定値にする。採番すると
「2 行目が入りうる」形を作ることになる。出ていく先は子表に置き、差分を取らずに消して
入れ直す (書き手が並べ替えたときに古い並びが残らない)。2 つの表への書き込みは D1 の
`batch()` で 1 つにまとめる。途中で落ちて「名前はあるのに出ていく先が空」の姿が表に
出ないようにするため。

**経歴の年表は出さない。** 作ってみたうえで落とした。個人サイトの `/about` に学歴や
資格を並べると、読み手が最初に受け取るのが履歴書になる。職務経歴は別に持っているので、
ここは「いま何をしていて、何を信じているか」に絞る。

**無いときは null で通し、404 にしない。** `/about` はヘッダーのナビが常に指している
行き先なので、初回同期の前に「そんなページは無い」と答えるのは嘘になる。「準備中」の
一枚に倒し、`noindex` を立てる。

⚠️ **microformats の殻だけは、プロフィールが無くても立てる。** トップの代表 h-card
(名前・顔・サイトへの参照) と、記事末尾の `p-author h-card` がそれにあたる。自己紹介や
出ていく先は出さなくてよいが、この 2 つが消えると Bridgy Fed から見て「誰のサイトか・
誰が書いたか」が分からなくなり、**橋が黙って架からなくなる**。既定の名前と顔は
`app/lib/profile-fallback.ts` が 1 か所で持つ。

## 帰結 / Consequences

- 良い面: 自己紹介の書き換えがデプロイを要さなくなる。3 か所が 1 つのデータを読むので
  写しが古びない。
- 良い面: 記事の同期と仕組みを共有したので、本文を MDAST に組む経路・合成ハッシュ・
  アセット URL の解決・画像の寸法埋め込みが 1 つずつになった。短文 (#412) と発表資料
  (#415) も同じものを使える。
- 悪い面: 同期の経路が 1 本増えた。`profile.md` のフロントマターが読めないと、その回の
  同期でプロフィールだけがスキップされる (記事は通る)。
- 悪い面: 出ていく先の種類は `app/lib/social-platforms.ts` の一覧に縛られる。知らない
  `platform` を書いた行はファイルごとスキップになるので、新しい先を出すにはコードを
  1 行足すことになる。アイコンがコンポーネントの参照である以上、避けられない。
- 検証方法: `profile-refresh.service.test.ts` が同期の決め (ハッシュ一致で読まない /
  読めなければ前の姿を残す / 消えたら掃除する / infra 障害は throw) を固定する。
  microformats の殻は `hero-section.mf2.test.tsx` と `author-note.mf2.test.tsx` が、
  **プロフィールが無いときも印が立つこと**を含めて見張る。
