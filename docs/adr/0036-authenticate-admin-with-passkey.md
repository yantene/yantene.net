# 0036. 管理者を passkey で認証し、セッションを KV に置く

- Status: Accepted
- Date: 2026-09-12
- Deciders: @yantene

## Context / 背景

管理者としてログインする経路を設ける (#437)。ログイン中だけ下書きを読み、Web から
Markdown を編集してコンテンツリポジトリにコミットできるようにするためで、認証はその土台になる。

いまサイトにある「認証らしきもの」はどちらも役に立たない。

- 読み手のセッション ([ADR 0011](0011-reader-session-in-kv.md)) は匿名で、
  推測できない識別子を配るだけ。誰であるかを確かめる仕組みを持たない
- staging の BASIC 認証は「staging 全体を人目から隠す」ための別のレイヤーで、
  production には掛かっていない (environments.md)

この認証に求めるものは 4 つある。

1. **利用者は 1 人。** 招待も役割分担も要らない。守るのは「自分以外が入れないこと」だけ
2. **フィッシング耐性。** 入られると記事を書き換えられ、コンテンツリポジトリにコミットできる。
   偽サイトに打ち込んで渡せる秘密を持たせたくない
3. **手元でも同じ経路で動くこと。** 下書きを `pnpm dev` で確かめられるようにする
   (#461) のが目的の一つで、そこだけ認証を迂回する作りにすると、**迂回路のほうが
   本番にも残る**
4. **読み手の要求を重くしないこと。** Worker は 1 つのバンドルで、記事を読みに来た人の
   要求もこれを読む。管理者 1 人のための重さを全員に払わせない

## 検討した選択肢

- **案 A: Cloudflare Access (Zero Trust) に寄せる** — `/admin/*` に Access を張り、
  Worker は `Cf-Access-Jwt-Assertion` を検証する。
  - Pros: 認証のコードをほぼ書かない。IdP・ワンタイムコード・ハードウェアキーは
    Cloudflare が面倒を見る。無料枠で足りる。すでに Cloudflare に寄せたサイトなので
    運用の毛色も揃う。
  - Cons: **localhost に Access は張れない。** 手元で下書きを見るには dev 専用の
    抜け道が要り、要件 3 に正面から反する。PR ごとのプレビュー URL (workers.dev) にも
    その都度設定が要る。認証の実体がリポジトリの外に出るので、`wrangler.jsonc` を
    読んでも誰が入れるのか分からない。
- **案 B: パスワード + セッション** — secret にハッシュを置き、フォームで照合する。
  - Pros: 実装が最も軽い。どの環境でも同じように動く。
  - Cons: フィッシング耐性が無い。偽のログイン画面に打ち込めばそのまま渡る。
    打ち間違いを試し続けられるので、回数制限も自前で要る。secure by default から一段弱い。
- **案 C: IndieAuth** — サイト自身を identity にする。
  - Pros: Micropub (#418) を受けるなら認可の経路を共有できた。Webmention を受けている
    サイトとして IndieWeb の流儀に揃う。
  - Cons: 自前で IdP を建てることになり、管理者ログインだけのためには重い。
    #418 は管理画面を作る判断とともに閉じたので、共有する相手がいなくなった。
- **案 D: passkey (WebAuthn)** — 公開鍵を登録し、署名でログインする。
  - Pros: パスワードを持たない。署名は origin に紐づくので、偽サイトに渡しても使えない
    (要件 2)。localhost は WebAuthn が secure context として特別扱いするので、手元でも
    同じ経路が動く (要件 3)。
  - Cons: 登録した端末を失うと入れない。検証を自分で持つことになる。

## 決定

**案 D。passkey (WebAuthn) で認証し、発行したセッションを KV に置く。**

案 A は要件 3 で落ちる。手元で下書きを見られるようにすること自体がこの一連の変更の
目的なので、そこに抜け道を掘る前提の認証は選べない。案 B は要件 2 で落ちる。案 C は
守る相手 (#418) がいなくなった。

### 検証は自前で書く

WebAuthn のライブラリは入れない。バンドルを実測して決めた。

|                                 | Worker バンドル    | 依存 | 備考                                      |
| ------------------------------- | ------------------ | ---- | ----------------------------------------- |
| `@simplewebauthn/server` 14     | +306KB (gzip 84KB) | 10   | `reflect-metadata` + ASN.1 / X.509 一式   |
| `@passwordless-id/webauthn` 2.4 | +31KB (gzip 13KB)  | 0    | DER → raw の変換に取りこぼしがある (下記) |

重さのほとんどは**アテステーション証明書の検証**のためにある。どの製造元のどの型番の
認証器かを証明書の連鎖で確かめる機能で、「この型番の認証器しか許さない」という運用に
要る。**登録するのは自分の端末だけなので、この検証はもともと行わない。** 払う相手の
いない重さを、記事を読みに来た人全員の要求に載せることになる (要件 4)。

軽いほうは DER の ECDSA 署名を Web Crypto の raw 形式に直す関数が、`r` または `s` が
32 バイト未満に縮んだ場合を扱えない。DER は整数を最小の長さで書くので、値が 2^248 未満
なら 1 バイト縮む。**約 1/128 のログインが理由なく失敗する。**

自前で書く範囲は、CBOR の部分デコード・COSE 公開鍵から `CryptoKey` への変換・
authenticator data のパース・DER から raw への変換・チャレンジと origin の照合に留まる。
**署名の検証そのものは Web Crypto が行う。** 暗号を実装するのではなく、仕様どおりに
値を並べ替えて渡す部分だけを持つ。既存の OGP パーサや Webmention の検証と同じ扱いにする。

### RP ID は環境ごとに別

`yantene.net` / `staging.yantene.net` / `localhost` は WebAuthn から見れば別の RP なので、
passkey は環境ごとに登録する。揃えようとすると RP ID を親ドメインに広げることになり、
署名が効く範囲を必要以上に広げる。**揃えない。** 手元と staging と production で
別々に登録する。

### 最初の 1 本をどう登録するか

誰でも登録できてはならない。

- 資格情報が 1 本も無いときだけ、secret `ADMIN_REGISTRATION_TOKEN` を示した要求が登録できる
- 1 本でもあるときは、**ログイン済みでなければ追加登録できない**
- secret が無ければ登録の経路そのものを閉じる (fail-loud)

端末を失うと入れなくなるので、passkey は複数登録できる形にする。

### セッションは KV に置き、読み手のものと混ぜない

読み手のセッション ([ADR 0011](0011-reader-session-in-kv.md)) とは別の cookie・別の
キー空間にする。混ぜると「その日どの記事を読んだか」と「記事を書き換えられる権限」が
同じ値にぶら下がり、片方の都合でもう片方の寿命や属性を動かすことになる。

- `SameSite=Strict` — 管理画面に外から辿り着く経路は無い。読み手のセッションが `Lax`
  なのは「リンクを踏んで来た人も同じ人として扱う」ためで、こちらにその要求は無い
- `HttpOnly` / `Secure` (development 以外)
- 寿命は読み手のもの (400 日) より短く、使うたびに延ばす

チャレンジも KV に置く。使い捨てで、短い期限を付ける。

### 管理者が見ている応答はキャッシュさせない

ログイン中の応答は `Cache-Control: private, no-store` にする。`Vary: Cookie` だけでは、
経路のどこかに載る危険が残る。載った先で剥がす手立ては無い。

## 帰結 / Consequences

- 良い面:
  - 打ち込んで渡せる秘密がサイトに存在しない。偽のログイン画面を作られても使えない
  - 手元・staging・production が同じ経路で動く。dev だけの抜け道を作らずに済む
  - 読み手の要求が重くならない。新しい実行時依存を 1 つも足さない
  - 認証の実体がリポジトリの中にある。誰が入れるかは D1 の表を見れば分かる
- 悪い面・トレードオフ:
  - **登録した端末をすべて失うと入れない。** 複数登録できるようにして緩めるが、
    消える可能性のある鍵を持つこと自体は変わらない。最後の 1 本を失ったときは、
    D1 の表を `wrangler d1 execute` で空にして bootstrap からやり直す
  - 環境ごとに登録し直す手間がある (RP ID を揃えない判断の裏返し)
  - WebAuthn の検証を自分で持つ。仕様が動けば追随するのは自分
  - アテステーションを見ないので、「どんな認証器で登録したか」は分からない。
    登録の入口を守ることでこれを補う
- 検証方法 / 今後の宣言:
  - 検証の各段 (チャレンジ・origin・RP ID ハッシュ・フラグ・署名) について、
    **落ちるべき入力で落ちることをテストで固定する**。通る入力が通ることだけを
    確かめると、照合を 1 つ消しても気づけない
  - 署名は ES256 と RS256 の両方で、DER の `r` / `s` が縮んだ場合を含めて確かめる
  - 登録の入口は「資格情報が 0 本のとき」「1 本以上あってログインしていないとき」
    「ログイン中」の 3 通りをテストで固定する
