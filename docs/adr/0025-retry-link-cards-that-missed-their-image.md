# 0025. リンクカードの絵の取り逃しを別の状態として持ち、短い期限で取り直す

- Status: Accepted
- Date: 2026-08-15
- Deciders: @yantene

## Context / 背景

[ADR 0014](0014-link-cards-from-ogp-only.md) でカードに期限を持たせた。取れたものは
14 日、取れなかったものは 1 日。成否を**カード単位**で持つ設計で、絵については「有無」
しか覚えていない。

ここに穴があった。**`og:image` は書かれているのに写しだけ作れなかったとき、題が取れて
いればカードは「取得できた」側に落ちる。** 絵の無いカードとして 14 日固定になり、相手が
すぐ復帰しても直らない。

実際に踏んだ ([#255](https://github.com/yantene/yantene.net/issues/255))。
`https://github.com/yantene/yantene.net` のカードから絵が消えていて、
`opengraph.githubassets.com` が断続的に `429 Too Many Requests` を返していた。1 発目だけ
429、以降は 200 で 37KB の PNG が返る。HTML も画像も上限内で、名乗りを変えても同じ
なので UA ブロックでもない。ただのレート制限で、次に叩けば取れるものだった。しかも
`fetchCapped` が `!response.ok` を undefined に畳むため、**ログにも残っていなかった**。

こちらから見れば「絵が無い」と「絵を写せなかった」は別のことだ。前者は何度試しても
同じで、後者は次に試せば取れるかもしれない。この区別を持っていなかったのが原因で、
持たせるにはカードの状態を 1 つ増やすことになる。

## 検討した選択肢

- **案 A: 絵を写せなかったらカードごと「取れなかった」にする**
  - Pros: 状態を増やさずに済む。1 日で取り直される。
  - Cons: 題も説明も取れているのに素のリンクへ落ちる。ADR 0014 の「画像は取れなくても
    カードは成立する」という線引きを、相手のレート制限のたびに越えることになる。
- **案 B: 絵を持たないカードをまとめて短い期限にする (列を増やさない)**
  - Pros: スキーマを触らずに済む。`has_image = 0` を見るだけ。
  - Cons: `og:image` を出していない相手のカードまで毎回叩き直す。そういうカードは
    珍しくないので、1 回 40 枚の枠が「取り直しても何も変わらないもの」で埋まる。
- **案 C: 絵の状態を 3 通りで持ち、取り逃しにだけ短い期限を与える**
  - Pros: 取り直す価値のあるものだけを取り直せる。何が起きたかが行に残るので、
    後から数えられる。
  - Cons: 列が 1 つ増える (migration が要る)。「取り逃し」の判定を fetcher が持つ。

## 決定

**案 C を採る。カードの絵を `stored` / `absent` / `missed` の 3 通りで持ち、`missed` の
カードは 24 時間で古いとみなす** (取れなかったカードと同じ刻み)。

線引きはこうする。

- **`missed` にするのは、`og:image` を取りに行って応答が得られなかったときだけ。**
  レート制限・不調・時間切れ・大きすぎがこれに当たる。**載せられない型 (SVG など。
  ADR 0014) は `absent`。** 取り直しても結論が変わらないため。
- **favicon の取り逃しは数えない。** `rel=icon` が書かれていない相手には慣例の
  `/favicon.ico` を試すので、置いていないサイトでは毎回取れない。これを取り逃しに
  数えると、そういう相手のカードが短い期限で永久に回り続ける。
- **取り逃したことは info で残す。** #255 が直しにくかった半分は、無音だったこと。
  絵の無いカードと絵を取り逃したカードは、出来上がりが同じで見分けが付かない。
- **D1 は `has_image` と `image_missed` の 2 列で持つ。** 3 通りに畳むのは infra の
  仕事で、ドメインは 1 つの状態として扱う。両方立った行は書かない。
- **期限の境目は 3 つともドメインが決めて渡す** (`staleCutoffs`)。SQL の 3 つの枝は
  重ならないように書く。重ねると、期限の大小を変えたときに黙って長いほうが効く。

## 帰結 / Consequences

- 良い面
  - レート制限のような一時的な失敗から、次の refresh で戻る。14 日固定ではなくなった。
  - 取り逃しがログに出るので、絵の無いカードを見たときに原因を追える。
  - 絵を持たない相手のカードは 14 日のままで、取り直す量は増えない。
- 悪い面・トレードオフ
  - 列が 1 つ増えた。**既存の行は `image_missed = 0` なので、いま絵の欠けているカードは
    14 日の期限が切れるか force refresh を流すまで直らない。**
  - **`og:image` が恒久的に 404 の相手は、refresh のたびに取り直され続ける。** 取れな
    かったカードを 1 日で取り直すのと同じ性質のもので、ADR 0014 が既に受け入れている。
  - **取り逃したときも前回の写しは捨てる。** 絵は次に取れるまで出ない。写しを残して
    「絵はある」ことにし続ける案は採らない。相手が絵を差し替えたときに古い絵を出し
    続けることになり、それは取り逃しより静かな壊れ方だから。
  - refresh は cron ではなくコンテンツの push で走るので、「24 時間」は「次の refresh で
    取り直す資格ができる」という意味しかない。
- 検証方法 / 今後の宣言
  - 期限の刻みは `link-card.entity.test.ts`、SQL の枝は `link-card.repository.test.ts`、
    取り逃しの判定と記録は `ogp-link-card-fetcher.test.ts`、状態の受け渡しは
    `link-cards-refresh.service.test.ts` で固定してある。
  - **この 3 通りは絵にだけ持たせる。** 相手の応答の形をカードの状態に写し取り始めると
    際限が無いので、増やしたくなったらまずここに書いた線引きを読み直すこと。
