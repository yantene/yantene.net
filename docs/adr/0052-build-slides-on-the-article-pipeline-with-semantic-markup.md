# 0052. スライドは記事と同じ経路の上に自前で組み、原文には意味だけを書かせる

- Status: Accepted
- Date: 2026-11-17
- Deciders: @yantene

## Context / 背景

発表で使うスライドをサイトに置きたい。LT や技術イベントの登壇に耐える表現力 (ページ送り、
段階表示、トランジション、全画面、印刷) が要る。

制約が 4 つある。

- **ビルドの段が無い。** コンテンツは push すると同期されるだけで、Worker が Markdown を
  読んで D1 と R2 に載せる ([ADR 0034](0034-artifacts-as-content-source-of-truth.md))。
- **本文は MDAST で持ち、React で描く** ([ADR 0005](0005-mdast-over-html-rendering.md))。
  数式、Mermaid、リンクカード、アセット URL の書き換えは、この経路にある。
- **CSP が厳しく、inline style を書かない** ([ADR 0007](0007-strict-csp-outside-development.md))。
- **クローラーにも、JavaScript が動かない読み手にも中身が届く。**

## 検討した選択肢

何で再生するか。

- **案 A: Marp** — Markdown にディレクティブを足して書き、marp-core が HTML と CSS にする。
  - Pros: 画像の分割レイアウトとヘッダー・フッターが記法 1 つで書ける。
  - Cons: 変換が markdown-it なので、経路が記事と 2 本になる。数式・Mermaid・リンクカード・
    アセットの扱いを 2 回作ることになり、変換済みの HTML を R2 に置くことになる。発表用の
    機能 (段階表示の出し分け) は marp-cli の側にあり、サイトに載せるなら作り直す。
- **案 B: reveal.js** — 実行時のエンジンに、自前で描いた `<section>` を渡す。
  - Pros: 段階表示・要素の変形・発表者画面が厚い。
  - Cons: 画面に合わせて縮める処理が要素の style を触る。エンジンのやり方に合わせて、
    CSP と inline style の決まりに例外を作ることになる。
- **案 C: 記事の経路の上に自前で組む** — 動きはブラウザの機能で賄う。
  - Pros: 変換の経路が 1 本のまま。CSP と inline style の決まりに最初から合わせて作れる。
    読み込むのは自前の小さなスクリプトだけ。
  - Cons: 段階表示と入れ替えの組み合わせを自分で持つ。壊れたときに頼れる実装が無い。

原文に何を書かせるか。

- **案 D: 見た目の指定を書かせる** — 配置、段組み、大きさ、色、トランジション。
  - Pros: 書き手が思いどおりの絵を作れる。
  - Cons: 見た目の調整に時間が溶ける。デッキごとに見た目がばらつき、テーマを直しても
    過去のデッキは直らない。原文を記事として読めなくなる。
- **案 E: 意味だけを書かせる** — 置き方は、意味と中身の形から決める。
  - Pros: 書き手は中身だけを考えればよい。テーマを直せば全部のデッキが揃って変わる。
    原文がそのまま読み物になる。
  - Cons: 規則で決まる置き方に、書き手が口を出せない。

## 決定

**案 C と案 E を採る。**

### 原文は記事と同じ Markdown で、意味の語彙に当てる

`slides/<slug>.md` を記事と同じ経路 (`parseMarkdownBody`) で MDAST にし、R2 に置く。
ページに切るのは描くときで、`app/lib/slides/deck.ts` の `paginate` が 1 か所で決める。

| Markdown                      | スライドでの姿                                     |
| ----------------------------- | -------------------------------------------------- |
| フロントマター                | 表紙 (必ず 1 枚目)                                 |
| `#`                           | 章の扉                                             |
| `##`                          | 1 ページ。見出しがページの題                       |
| 地の文の段落                  | 語り。スライドには出ず、読み物の側に本文として出る |
| `-` のリスト                  | 箇条書き                                           |
| `1.` のリスト                 | 1 項目ずつ出す                                     |
| 画像だけの段落                | 図                                                 |
| 表・引用・Alert・コード・数式 | そのまま 1 つの塊                                  |
| 脚注                          | 最後の「References」のページ                       |
| `. . .`                       | 間。そこから下を 1 段遅らせる                      |

**見た目の逃げ道は持たない。** 生の HTML はスライドに運ばず、クラスも配置も書けない。

### 置き方は中身の形から決まる

ページの置き方 (`SlideLayout`) は `paginate` が決め、書き手は選べない。題だけなら一言の
ページ、図 1 つだけなら図を全面に、図とほかの塊なら図の縦横比で上下か左右に、引用だけ・
表だけなら真ん中に。縦横比は同期のときに画像へ埋めた寸法から読む (記事の画像と同じ処理)。

同じ原文からは必ず同じデッキができる。`paginate` は時計も乱数も読まない純粋関数で、
サーバーとブラウザの両方が同じ原文を切る (切った結果を loader の応答に載せて運ばない)。

### 入りきらない量は縮めず、同期のときに警告する

1 ページの量 (項目・字・コードの行・表の行と列) が目安を超えたら、同期の結果に警告として
出す (`app/lib/slides/overfull.ts`)。スライドは同期し、描く。はみ出した分は枠で切れる。
目安は数であって、描画の実測ではない。

### 動きはブラウザの機能で賄う

| 欲しいもの       | 何で作るか                                               |
| ---------------- | -------------------------------------------------------- |
| 拡大縮小         | 16:9 の枠 (`aspect-ratio`) と、枠の幅に対する比 (`cqw`)  |
| ページ送り       | キー、クリック、スワイプ。現在地は URL のハッシュ (`#3`) |
| 段階表示         | 塊に段の番号を振り、先の段にクラスを付けて CSS が隠す    |
| ページの入れ替え | View Transitions。章をまたぐときだけ種類を変える         |
| 全画面           | Fullscreen API                                           |
| 印刷             | `@media print` と名前付きの `@page` で 1 ページ 1 枚     |

`style` 属性は書かない。可変なのは静的なクラスの段階だけで、番号付きリストの「いくつ目まで
出すか」も `data-revealed` の段階として CSS に並べてある。

### サーバーは全ページを縦に並べて描く

サーバーの出力は全ページで、JavaScript が動き出してから `data-playing` を立てて 1 ページずつ
見せる。動かない環境・クローラー・印刷には、縦に並んだ全ページが届く。最初の描画は必ず
1 ページ目で、ハッシュを読むのは描いたあと (サーバーはハッシュを見られない)。

ページの下には、同じ原文を記事と同じ描き方で読める形にして置く (Transcript)。語りは
ここにだけ出る。

### 公開範囲を持たない

作品 ([ADR 0042](0042-keep-works-as-their-own-content-kind.md)) と同じで、出したくない
スライドは push しない。記事と違い、フィードには流す (時系列に増えるものなので)。

## 帰結 / Consequences

- 良い面: 数式・Mermaid・リンクカード・アセットの扱いが記事と同じになり、スライドのために
  変換を 2 つ持たない。テーマ (`slide.css`) を直せば、過去のデッキ全部が揃って変わる
- 悪い面・トレードオフ:
  - **全部のデッキが同じ顔になる。** 見た目で驚かせる手は使えない。
  - **置き方に口を出せない。** 規則が合わないページでは、原文の書き方を変えるか、意味の
    語彙を足すことになる。
  - 段を隠すのは再生中だけなので、JavaScript が動かない読み手には全部が最初から見える。
  - View Transitions の無いブラウザでは、ページは動かずに切り替わる。
  - 入りきらない量の目安は実測ではないので、外れることがある。
- 守るための仕組み:
  - `deck.test.ts` — 語彙の当て方、置き方の決まり、同じ原文から同じデッキができること
  - `slide-navigation.test.ts` — 送り方と戻り方、ハッシュの読み書き
  - `slide-deck.test.tsx` — サーバーが全ページを描くこと、`style` 属性を書かないこと、
    語りがスライドに出ないこと
