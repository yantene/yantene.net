# 0026. リンクカードは短い不調の間だけ前回の中身で持ちこたえる

- Status: Accepted
- Date: 2026-08-18
- Deciders: @yantene

## Context / 背景

[ADR 0014](0014-link-cards-from-ogp-only.md) で「取れなければ素のリンクに落とす」と決めた。
この判断自体は今も正しい。相手のサイトの不調でこちらの同期を止めないための線引きで、
外部サイトの応答は入力であってこちらの状態ではない。

ただし**落とし方**に穴があった。取得に失敗すると、行の題も説明も NULL で上書きされる。
つまり**前回きちんと取れていたカードでも、相手が一瞬落ちただけで素のリンクへ落ちる**。

問題は、そこから戻るのに時間がかかることだ。refresh は cron ではなく**コンテンツの
push で走る** (ADR 0004)。取れなかったカードの期限は 24 時間だが、これは「24 時間後に
取り直す」ではなく「次の refresh で取り直す資格ができる」という意味しかない。記事を
1 週間書かなければ、素のリンクのまま 1 週間出続ける。

相手の 30 秒の不調と、こちらの記事が 1 週間みすぼらしくなることが釣り合っていない。

## 検討した選択肢

- **案 A: いまのまま。取れなければ必ず中身ごと捨てる**
  - Pros: 出しているものが常に「最後に取れた中身」で、古い写しを見せることが無い。
    状態が 3 通りのままで、[ADR 0025](0025-retry-link-cards-that-missed-their-image.md)
    が引いた「カードの状態を増やさない」線の内側に収まる。
  - Cons: 一時的な不調が記事の見た目に直撃する。しかも戻るのが次の push 次第なので、
    復旧までがこちらの都合で決まらない。
- **案 B: 前回の中身を無期限に持ちこたえる**
  - Pros: 実装が小さい。一時的な不調は完全に吸収できる。
  - Cons: **恒久的に死んだリンクが古い中身を永久に出し続ける。** 失敗のたびに
    `fetched_at` が進むので行は古くならず、force refresh を流しても同じ失敗の経路を
    通るだけで消えない。直すには D1 を直接叩くしかない。ADR 0025 が「取り逃しより
    静かな壊れ方」と呼んだものの、期限の無い版になる。
- **案 C: 持ちこたえる期間に上限を置く**
  - Pros: 一時的な不調は吸収し、恒久的な死は素のリンクへ落として自然に回収する。
  - Cons: 列が 1 つ増える (migration が要る)。「一時的」と「恒久的」の境目を数字で
    決める必要がある。

## 決定

**案 C を採る。取得に失敗したとき、前回の中身があれば 3 日を上限に持ちこたえる。**

線引きはこうする。

- **持ちこたえるのは中身が丸ごと。** 題・説明・絵の写しをまとめて残す。題だけ残して絵を
  消すと、相手が一瞬落ちただけでカードの形が変わる。**どうせ古いものを見せているので、
  古さの単位を揃えるほうが読み手にとって一貫している。**
- **上限は失敗の起点から 3 日。** 越えてもなお失敗したら中身を捨て、ADR 0014 の既定
  (素のリンク) に戻す。24 時間の刻みで取り直すので、諦めるまでに少なくとも 3 回は試す。
  相手の不調が 3 日続くなら、それはもう「一時的」ではない。
- **これは壁時計の保証ではない。** 判定されるのは「3 日を越えてから、次に取りに行って
  失敗したとき」でしかない。push が来なければ 3 日は 3 週間にもなる。**上限は「いつか
  必ず回収される」ことの保証であって、「3 日で消える」ことの保証ではない。**
- **列は `fetch_failed_since` (時刻・NULL 可) で持つ。** 真偽値では上限を測れない。
  失敗が続く間この列は動かさず、`fetched_at` だけが進む。両方を進めると上限に永久に
  届かず、案 B と同じものになる。
- **NULL でない行は必ず中身を持つ。** 中身の無い行 (title が NULL) は持ちこたえるものが
  無いので常に NULL。この対応のおかげで、2 つの列の組が 3 つの状態に 1 対 1 で対応し、
  行からエンティティへの変換に「ありえない組」が残らない。
- **期限の境目はドメインが決めて渡す** (`staleCutoffs`)。いまの値は取れなかったカードと
  同じ 24 時間だが、同じだからと使い回さず別の項目にする。片方だけ変えたときに SQL と
  エンティティが黙って食い違うため。ADR 0025 が `imageMissed` で置いたのと同じ理由。
- **持ちこたえた URL は refresh の結果に `kept` として出す。** `failed` に混ぜない。
  混ぜると、運用者が「素のリンクに落ちた」のか「カードのまま古い中身が出ている」のかを
  見分けられない。**この 2 つは見た目の壊れ方が違う。**

### ADR 0025 の線を越えることについて

ADR 0025 はこう書いている。

> **この 3 通りは絵にだけ持たせる。** 相手の応答の形をカードの状態に写し取り始めると
> 際限が無いので、増やしたくなったらまずここに書いた線引きを読み直すこと。

読み直した上で越える。理由は 2 つある。

1. **上限があるので「際限が無い」に当たらない。** 0025 が退けたのは、写しを残して
   「絵はある」ことにし**続ける**案だった。ここで足すのは有限の猶予で、越えれば
   0014 の既定へ戻る。状態が増えるのではなく、既存の 2 状態の間に減衰の途中が入る。
2. **0025 が挙げた危険が、この状況では成り立ちにくい。** 0025 の懸念は「相手が絵を
   差し替えたときに古い絵を出し続ける」ことだった。**それが起きるのはページが生きて
   いるときで、絵の取得だけが失敗した場合の話だ。** こちらはページごと取れていない
   ので、その間に相手が何をしたかは観測できないし、差し替えられたかどうかも分からない。

したがって 0014 も 0025 も Deprecated にしない。どちらの決定も撤回していない。

## 帰結 / Consequences

- 良い面
  - 相手の短い不調が記事の見た目に出なくなった。次の push を待たずに済む。
  - 恒久的に死んだリンクは 3 日で素のリンクに戻る。放置しても自然に回収される。
  - `kept` と `failed` が分かれたので、refresh の結果から壊れ方を見分けられる。
- 悪い面・トレードオフ
  - 列が 1 つ増えた。**既存の行は `fetch_failed_since` が NULL なので、この変更の前に
    素のリンクへ落ちたカードは戻らない。** 次に取れたときに戻る。
  - **持ちこたえている 3 日の間、運用者がカードを消す手段は無い。** force refresh も
    同じ失敗の経路を通る。急ぐなら D1 を直接叩くことになる。案 B と違って有限なので、
    そのための入口は用意しない (使う場面が来ないうちに腐る)。
  - **古い中身を見せている間、読み手にはそれと分からない。** カードに「古い」印は
    出さない。3 日という幅では、印を出すほうが情報として過剰だと判断した。
  - 相手が落ちている間も 24 時間の刻みで叩き続ける。落ちているサイトへの追加の負荷に
    なるが、これは取れなかったカードを 1 日で取り直すのと同じ性質のもので、ADR 0014 が
    既に受け入れている。
- 検証方法 / 今後の宣言
  - 上限の刻みと起点の据え置きは `link-card.entity.test.ts`、SQL の 4 つの枝が重ならない
    ことは `link-card.repository.test.ts`、R2 の掃除と `kept` / `failed` の振り分けは
    `link-cards-refresh.service.test.ts` で固定してある。
  - **枝が重ならないことは、件数では確かめられない。** SQL の `OR` は枝が重なっても行を
    2 度返さない。期限を枝ごとに別々に動かして初めて差が出るので、テストもそう書く。
  - **持ちこたえる対象を「取得の失敗」より広げない。** 相手が 200 を返しながら中身を
    変えた場合は、それが最新なのでそのまま反映する。
