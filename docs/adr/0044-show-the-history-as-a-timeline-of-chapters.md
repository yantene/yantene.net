# 0044. 経歴を章で束ねた年表として `/about` の末尾に出す

- Status: Accepted
- Date: 2026-09-16
- Deciders: @yantene

## Context / 背景

[ADR 0041](0041-keep-the-profile-in-the-content-repository.md) は「経歴の年表は出さない。
作ってみたうえで落とした」と決めた。理由は「個人サイトの `/about` に学歴や資格を並べると、
読み手が最初に受け取るのが履歴書になる」ことだった。

その後、書き手は `profile.md` の本文の末尾に `## History` を書いた。高校・大学・社会人の
3 つの小見出しの下に、年を括弧で添えた箇条書きが並んでいる。**年表はすでに在る**ので、
残っている問いは「持つか」ではなく「どう描くか」になった。

当時の懸念そのものは今も正しい。名乗りの直下に学歴が並べば、顔・名前・短い自己紹介という
主役は押される。押さえたいのは「年表を持つこと」ではなく「読み手が最初に受け取るものが
履歴書になること」で、これは**置き場所と束ね方**で決まる。

## 検討した選択肢

- **案 A: 本文の Markdown のまま出す** — いまの姿。`## History` が MDAST として描かれる。
  - Pros: 何も作らなくてよい。
  - Cons: 年が `(2011)` という字として本文に埋まっている。箇条書きなので、年・出来事・
    補足の区別が読み手にも機械にも付かない。並び順を変えても見た目が変わらないので、
    これが時系列であることが伝わらない。
- **案 B: 本文の書き方を約束にして、描く側が拾う** — `## History` と `(YYYY)` を見つけたら
  年表として描く。
  - Pros: 書き手はいまの書き方を変えなくてよい。
  - Cons: 見出しの字を変えただけで静かに元の箇条書きに戻る。年を地の文から正規表現で
    取り出すので、`(2011 年ごろ)` のような字が «たぶん 2011» として通る。fail-loud に反する。
- **案 C: フロントマターに構造として持つ** — `profile.md` の `history` 欄。
  - Pros: VO が検証するので、書き損じはその回の同期が止まって理由を返す。`socials` と
    同じ形なので、保存・同期・描画の決めをそのまま写せる。
  - Cons: フロントマターが 11 件ぶん膨らむ。`## History` を本文から消す手間が 1 回要る。
- **案 D: `history.md` を独立した種別として立てる** — `works` と同じ形
  ([ADR 0042](0042-keep-works-as-their-own-content-kind.md))。
  - Pros: `profile.md` のフロントマターが短いまま。
  - Cons: VO・D1 の表・リポジトリ・同期経路・掃除の決めが一式増える。得られるのは
    「フロントマターが短い」だけで、`/about` の 1 節に対して釣り合わない。

## 決定

**案 C。** 経歴は `profile.md` のフロントマターの `history` に持ち、`/about` の末尾に
年表として出す。

```yaml
history:
  - chapter: 高校
    entries:
      - year: 2011
        text: 第 28 回 全国高等学校情報処理競技大会 愛知県予選会 個人優勝
  - chapter: 大学
    entries:
      - year: 2012
        text: セキュリティ・キャンプ中央大会 2012
        url: https://www.youtube.com/watch?v=Ki1qb9q4z8E
        note: CTF チーム優勝
```

0041 の懸念を押さえるのは、次の 2 つである。**どちらも見た目の好みではなく、この決定の
条件**なので、動かすなら 0041 の判断に立ち返ることになる。

- **置き場所は `/about` の末尾。** 長い自己紹介の本文と、作ったものより後に置く。
  名乗り (`ProfileCard`) にも本文の頭にも出さない。読み手が最初に受け取るのは顔・名前・
  短い自己紹介で、次が「何者か」の地の文、その次が「何を作ったか」。経歴はその後ろ
- **束ねるのは暦年ではなく章。** 高校・大学・社会人のような区切りは書き手が決める。
  暦年で束ねると、2012 年に 4 件寄る一方で 2013 〜 2015 年が空き、卒業と入学が同じ束に
  混ざる。人生の話は暦よりも章のほうで読める

**`text` と `note` は素の字。Markdown を解釈しない。** 本文から移すときに記法を落とす
手間を書き手に課すことになるが、ここで MDAST を通すと、1 行の補足のために本文と同じ
描画経路 (リンクカード・数式・画像の解決) を引き込むことになる。リンクは `url` の欄が
持つので、記法が要る話は本文の地の文へ回す。

**年と、書けるなら月まで。日と期間は持たない。** 続いていることは始まった年の出来事として
書く (「2018 年から Web 系受託開発」ではなく `year: 2018` に「Web 系受託開発を始める」)。
範囲を持つと札が「2018–」のような字になり、読み上げでも横並びでも意味を取りにくくなる。

**月は任意。** 卒業と入学は 3 月と 4 月と決まっているが、大会や合宿は覚えていないことが
ある。必須にすると、覚えていない月を埋めさせることになる。札は月まで書いてあれば
`2012-04`、無ければ `2012`。**混ざるのは承知の上**で、揃えるために書けない月を捏造する
ほうが悪い。

⚠️ 月を持たせずに出した版があり、そのときは「年だけを持ち、月日と期間は持たない」と
書いてあった。本文に書いてあった材料が年しか持っていなかったのでそう決めたが、書き手は
月まで書ける。**上の「範囲を持たない」理由は、点の出来事に月を添えることには当たらない**
ので、この段だけを書き直した ([#520](https://github.com/yantene/yantene.net/issues/520))。
新しい ADR を起こさなかったのは、決定の主題が同じだから — 0045 を立てると「経歴のことを
知るのに 2 本読ませる」ことになる。

**並べ直さない。** 章の順も章の中の順も、書き手が書いた順のまま出す。同じ年に卒業と入学が
並ぶとき、どちらを先に置くかを機械が決める理由が無い (`socials` と同じ決め)。

**保存は `profile_socials` と同じ平らな行。** 章を各行が持ち (`profile_history.chapter`)、
読み出しは `position` 順の 1 本の並び。章に畳み直すのは出す側 (`toPublicHistory`) で、
現れた順に畳む。章ごとの表を作らないので、upsert の「差分を取らずに消して入れ直す」も
そのまま使える。

⚠️ **子の insert は行数で切って複数文にする。** D1 は 1 文に 100 個までしかバインド
パラメータを受けない。経歴は 1 行が 8 個束ねるので、1 文にまとめると **13 件目を書いた
push で batch ごと落ち、経歴だけでなくプロフィールの同期まるごとが止まる**。しかも
手元のテスト (`createTestD1` は node:sqlite、上限 32766) では絶対に再現しない。
`article-embedding.command-repository.ts` と同じ手で切る。

**トップと記事の末尾は読まない。** DTO (`PublicProfile`) に載せず、`/about` のローダだけが
組む。記事を 1 本開くたびに 10 件以上の出来事を運ぶ理由が無い (短い自己紹介と長い自己紹介を
分けているのと同じ理屈。0041)。

⚠️ **h-card にも JSON-LD にも出さない。** 経歴は読み物として画面に出すもので、機械に
名乗る身元の一部ではない。生年月日と出身地を機械が読む形 (`dt-bday` / `birthDate`) で
持たないと決めたこと ([#508](https://github.com/yantene/yantene.net/issues/508)) と
同じ線引きなので、`dt-*` / `alumniOf` / `award` を足すと経歴の側からその線引きが崩れる。

**見た目の語彙は記事の年表と共有するが、コンポーネントは分ける。** 左の柱・点・縦の罫線は
`article-timeline` と同じに見えるが、あちらは記事 1 本を前提にした器で、スラグ・公開日・
要約・サムネイル・`h-feed` / `h-entry` を持つ。経歴にはどれも無く、出来事に `h-entry` を
付けるのは意味論的に嘘になる。点の色も意味が違う (あちらは公開月を 1 年の位相として表し、
こちらは色を持たない)。

## 帰結 / Consequences

- 良い面: 経歴が書き損じたまま出ることがない。年が数として入っているので、章の柱・年の札・
  出来事・補足を別の字として組める。
- 良い面: 書き換えは push だけで済む (0041 の狙いがそのまま経歴にも効く)。
- 悪い面・トレードオフ: `profile.md` のフロントマターが 11 件ぶん膨らむ。本文に散文として
  書けば済んだものを、構造として書くことになった。
- 悪い面: 0041 の「持たない」を覆したので、**置き場所と束ね方が緩むと当時の懸念がそのまま
  戻る**。規範 (`.claude/rules/product.md`) にこの条件を書いてあるが、機械は止めない。
- 悪い面: `profile_history` の行が読めなくなると、プロフィールを読むだけのトップと全記事
  ページが巻き添えになりうる。`InvalidHistoryEntryError` を `profileDataErrors` に入れて
  null に倒してあるが、VO を足すたびに同じ登録が要る。
- 悪い面・先送り: **`find()` が経歴まで読むので、トップと全記事ページが読み捨てる行を
  引いている** (`toPublicProfile` は経歴を見ない)。`Promise.all` で待ち時間は増えないが、
  D1 の読み取り行数と巻き添えの広さは増える。読み口を `find()` と `findHistory()` に
  分けるのが筋で、[#519](https://github.com/yantene/yantene.net/issues/519) に送った。
  **この ADR の「トップと記事の末尾は読まない」は、いまのところ読み手に運ぶもの
  (`PublicProfile`) の話でしかない。**
- 検証方法:
  - `profile-history.mf2.test.tsx` が microformats の印と `time` 要素が 1 つも無いことを
    見張る。
  - `pages.handler.test.ts` が JSON-LD の鍵の並びを固定し (経歴が混ざると落ちる)、章に
    畳み直す順が「現れた順」であることと、壊れた経歴の行で全記事ページが落ちないことを
    見る。
  - `profile-refresh.service.test.ts` が書き損じ (章の名前が無い・空の章・引用符付きの年・
    枠の外の年・出来事の字が無い・http(s) でない行き先) をスキップとして返すことを固定する。
  - `profile.command-repository.test.ts` の「D1 のバインドパラメータ上限」が、schema から
    列の数を数えて 1 文あたりのパラメータ数を見る (**欄を足したら落ちる**)。手元では
    超過を踏めないので、動かして確かめることができない。
  - `about.placement.test.tsx` が `/about` の節の並び (名乗り → 本文 → 作ったもの → 経歴) を
    固定する。**置き場所は見た目に出ない** — どの順に並べても「それらしく」出てしまうので、
    人の目では守れない。
