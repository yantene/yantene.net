# 0040. 記事に status を持たせ、全 status を同期し、読み取り口を既定で読み手向けにする

- Status: Accepted
- Date: 2026-09-13
- Deciders: @yantene

## Context / 背景

記事の公開範囲はフロントマターの `visibility` (`public` / `private`) で決めていた。
`private` を書いた記事は refresh が同期の対象から外し、既に同期済みなら D1 と R2 から
掃除する。配信側に除外条件を一切書かずに済むのが利点で、経路が増えても書き漏らしようが
ない。

この方式には取り返しのつかない副作用がある。

- **届いた Webmention が消える。** 送り手の名前・アイコン・本文はこちらの D1 にしか
  無く、コンテンツリポジトリのどこにも無い。取り下げると戻せない
- **閲覧数と人気スコアが消える。** 一度取り下げて出し直すと 0 から数え直しになる
- **手元でも見えない。** 同期されない以上、書きかけを画面で確かめる手段が無い

加えて `public` / `private` の 2 値では、「これから書くもの」と「もう出さないと決めた
もの」を区別できない。どちらも同じ `private` になる。

ログインが入った ([ADR 0039](0039-sign-in-with-a-magic-link.md)) ので、
**読み手には見せず、管理者には見せる**という区別が表現できるようになった。

## 検討した選択肢

- **案 A: `visibility` のまま、`private` も D1 に載せて配信側で除外する** — 列を足さず、
  各配信経路に `WHERE visibility = 'public'` を書く。
  - Pros: 変更が小さい。Webmention と閲覧数は残る
  - Cons: **2 値のままなので下書きと取り下げを区別できない。** そして除外条件を書く
    場所が経路の数だけ増える。product.md が退けたのはまさにこの形で、書き漏らしたときに
    漏れるのは「見せたくないもの」になる
- **案 B: status を足し、配信経路ごとに除外条件を書く** — 5 値に増やし、一覧・フィード・
  sitemap・検索・OG・関連記事・人気順それぞれに条件を書く。
  - Pros: 段階を表現できる
  - Cons: Cons は案 A と同じ。**経路は現在 16 箇所**あり、これから増える。新しい経路を
    書く人が条件を書き忘れても何も起きず、気づくのは漏れたあと
- **案 C: status を足し、読み取り口そのものを 2 つに分ける (採用)** — リポジトリの
  コンストラクタを private にし、`forReaders` / `forAdmin` の 2 ファクトリでしか作れなく
  する。どの status を通すかは**メソッドごとに固定**し、呼ぶ側は選べない。
  - Pros: 新しい経路を書く人は必ずどちらかを選ばされる。既定で漏れる形にならない
  - Cons: 既存 16 箇所の差し替えが要る。管理者に見せたい経路が増えるたびに
    `forAdmin` を渡す判断が要る

## 決定

**案 C。**`status` を 5 値で持ち、**どの status の記事も D1 / R2 に同期する**。
「同期しない記事」という概念は無くす。読み手から隠すのは配信の時点で行い、その除外は
リポジトリの作り方に畳み込む。

### status

フロントマターに `status` を書く。省略時は `published`。

| status      | 意味              | 一覧・フィード・sitemap・検索・関連記事・人気順 | URL 直打ち       | 管理者 |
| ----------- | ----------------- | ----------------------------------------------- | ---------------- | ------ |
| `published` | 公開              | 出る                                            | 見える           | 見える |
| `unlisted`  | 限定公開          | 出ない                                          | 見える (noindex) | 見える |
| `withdrawn` | 非公開 (取り下げ) | 出ない                                          | 404              | 見える |
| `draft`     | 執筆中            | 出ない                                          | 404              | 見える |
| `idea`      | アイデア段階      | 出ない                                          | 404              | 見える |

読み手から見た振る舞いは 3 種類 (公開 / 限定公開 / 隠す) しかない。`withdrawn` /
`draft` / `idea` は読み手に対しては同じで、違うのは管理者の一覧での意味づけだけ。
それでも 3 つに分けるのは、「これから書くもの」と「もう出さないと決めたもの」を
一覧で見分けたいため。

`unlisted` にクエリパラメータや署名は要らない。URL を知っていれば読める。守るのは
「一覧・検索・フィードから辿れないこと」と「検索エンジンに載らないこと」の 2 つだけで、
秘密にすることではない。

### 読み取り口は 2 つのファクトリでしか作れない

```ts
D1ArticleQueryRepository.forReaders(d1); // 読み手向け
D1ArticleQueryRepository.forAdmin(d1); // すべて
```

コンストラクタは private。`forReaders` が通す status は**メソッドごとに固定**する。

| メソッド      | 用途                           | 通す status              |
| ------------- | ------------------------------ | ------------------------ |
| `list`        | 一覧・フィード・sitemap        | `published`              |
| `search`      | 全文検索                       | `published`              |
| `findByIds`   | 人気順                         | `published`              |
| `findBySlugs` | 関連記事                       | `published`              |
| `findBySlug`  | 記事ページ・OG・原文・アセット | `published` + `unlisted` |

「一覧に出ない」と「URL で読める」の違いは、呼ぶ側の事情ではなく**メソッドの性質**
なので、ここに畳み込める。引数で渡せるようにすると、渡し忘れが漏れになる。

refresh は掃除の判定に全 status が要るので `forAdmin`。

### 読み手に届く索引には published しか入れない

検索の索引 (`articles_fts`) と人気順 (`view_log_score` の索引) は、リポジトリを
通らずに D1 を直接読む。ここを素通りさせると、**上位 N 件を下書きが埋めてから
`findByIds` が落とす**ため、結果が N 件に足りなくなる。

- 検索の索引には `published` の記事だけを入れる。他の status は索引から外す
- 人気順の SQL に `status = 'published'` を書く

### `visibility` が残っていたら記事ごとスキップする

旧書式の `visibility` が書かれた記事は、**読まずにエラーとして報告する**。`visibility`
を無視して既定の `published` に倒すと、`visibility: private` と書いたままの下書きが
黙って公開される。書式を移し忘れたことは、記事が出ないことで気づけばよい。

## 帰結 / Consequences

- 良い面: 取り下げても Webmention と閲覧数が残る。出し直せば元に戻る
- 良い面: 下書きが D1 と R2 に載るので、**本番に上げたまま管理者だけが読める**。
  staging へ上げて確かめる往復が要らなくなる
- 良い面: 新しい配信経路を書く人は `forReaders` / `forAdmin` を選ばされる。既定で
  漏れる形にならない
- 悪い面: 下書きも同期されるので、**本文が参照する URL のリンクカードを refresh が
  取りに行く**。まだ公開していない記事から外部への取得が起きる
- 悪い面: 記事数が増える。D1 の行と R2 の写しが、公開していないものぶんだけ増える
- 悪い面: 管理者に見せる経路を増やすたび、`forAdmin` を渡してよいかの判断が要る。
  渡した応答には `Cache-Control: private, no-store` が要る (経路のどこかに載ると、
  読み手に配られる)
- 検証方法: `forReaders` の各メソッドが `published` 以外を返さないことをリポジトリの
  テストで固定する。`findBySlug` だけは `unlisted` も返すことを別に固定する。
  コンストラクタが private なので、ファクトリを通らない生成は型が弾く
