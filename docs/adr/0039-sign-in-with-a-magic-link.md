# 0039. ログインはメールのマジックリンクで行い、トークンは POST でしか使わない

- Status: Accepted
- Date: 2026-09-13
- Deciders: @yantene

## Context / 背景

このサイトにログインの仕組みを置く。目的は 2 つある。

- **書き手 (管理者) が自分だと名乗れること。** 下書きの閲覧 (#437 / #466) と
  Web からの編集 (#467) が、これを前提にしている
- **この先、読み手もログインすること。** 知り合いだけに見せる記事と有償記事を計画して
  いる (#480)。読み手を入れる仕組みを、管理者のそれと別に持ちたくない

ここから制約が出る。

- **識別子はメールアドレスでなければならない。** こちらが先に持っているのは相手の
  アドレスであって、相手の端末ではない。「相手が登録してから、こちらが見分けて許可を
  出す」順しか取れない仕組みだと、知り合いに先回りして許可を置けない。有償記事なら
  控えと復帰のためにどのみちアドレスが要る
- **端末をまたぐ。** デスクトップで買ってスマートフォンで読む。読み手に同期の道具を
  要求できない
- **書き手は 1 人で、置き場は Cloudflare の中だけ。** 認証の基盤を別に建てて運用する
  額に見合わない

## 検討した選択肢

- **案 A: passkey (WebAuthn)** — 端末の認証器で署名する。
  - Pros: 総当たりも使い回しも効かない。メールの到達に依存しない
  - Cons: **識別子を持たない。** 事前に許可を置けず、必ず「相手が登録する → こちらが
    見分ける」順になる。端末をまたぐには相手側の同期に頼る。結局アドレスを横に置く
    ことになり、資格情報を 2 種類維持することになる
- **案 B: パスワード** — アドレスと合言葉を預かる。
  - Pros: 誰でも知っている。メールの到達に依存しない
  - Cons: **預かりたくないものを預かる。** ハッシュの選定・使い回しの被害・再発行の
    経路 (結局これがマジックリンク) が全部こちらの責任になる。得るものが無い
- **案 C: 外部の身元 (Google / GitHub でログイン)** — OIDC に委ねる。
  - Pros: 到達率も総当たり対策も相手持ち
  - Cons: 読み手にアカウントの種類を要求する。**アドレスは結局その先から貰う**ので、
    識別子の話は解決しない。連携先ごとに同じアドレスが別人になる事故が付いて回る
- **案 D: メールのマジックリンク** — アドレス宛に 1 回きりの URL を送る。
  - Pros: 識別子がそのまま資格情報。事前に許可を置ける。端末をまたげる。預かる秘密が
    無い (トークンはこちらが作って捨てる)
  - Cons: メールの到達と遅延に乗る。**リンク検査に先に踏まれる**という固有の事故がある

## 決定

**案 D を採る。識別子はメールアドレス、資格情報はマジックリンク、管理者と読み手を
区別しない。** 入口は `/sign-in` の 1 つで、入ったあとに何ができるかを役割が決める。

### トークンは `GET` では使わない

マジックリンク固有の事故は、**会社のメールのリンク検査が 1 回きりのトークンを本人より
先に踏み潰す**こと。本人がリンクを押したときには、もう使われている。

そこで**使い切るのは `POST` だけ**にする。`GET /sign-in/callback` は何も消費せず、
押し場所のある画面を描くだけ。検査器は `GET` しかしないのでここで止まる。

ただし「同じブラウザから来たときだけ通す」では**端末をまたげない** (上の制約)。
そこで同じブラウザかどうかは*近道*としてだけ使う。

1. `POST /api/v1/sign-in` が乱数を 1 つ作り、トークンの行に書き、`SameSite=Lax` の
   cookie に預ける
2. `GET /sign-in/callback` で cookie と行が一致すれば、その場で使い切って入れる。
   **押す手間が無い** (同じブラウザ。webmail から踏んでも `Lax` なら送られる)
3. 一致しなければ確認の画面を出し、押させて `POST` する (別の端末)

`POST` は `Origin` を見る。ここを開けておくと、攻撃者が自分のトークンを他人のブラウザに
踏ませて**攻撃者としてログインさせられる** (login CSRF)。

### トークンは D1 に、ハッシュで置く

置き場を KV ではなく D1 にするのは、**引き当てと削除を 1 手 (`DELETE ... RETURNING`)
で済ませたい**ため。KV では読んでから消す 2 往復になり、同じリンクを同時に 2 回踏まれると
両方が通る。KV の削除は colo をまたいで伝わるまで時間がかかるので、消したはずのトークンを
別の colo が見つけられてしまう。

置くのは SHA-256 を通した値。**生の値は送ったメールの中にしか無い。** D1 の中身が
漏れてもログインはできない。合言葉と違って元が 256 bit の乱数なので、伸長は要らない。

寿命は 15 分。リンク検査に潰されない形にした以上、長く置く理由が無い。

### セッションは KV に置き、中身はアドレスだけ

読み手のセッション (ADR 0011) と同じ KV に、別の接頭辞で置く。持たせるのはアドレスと
時刻だけで、役割は持たせない。**役割は要求のたびに `ADMIN_EMAIL` と引き比べる。**
セッションに焼き付けると、管理者から外した相手が入ったままになる。

### いま入れるのは `ADMIN_EMAIL` の 1 つだけ

リンクを送る相手は `env.ADMIN_EMAIL` と一致するアドレスだけ。**このサイトに入れる
アドレスの集合は、いまこの 1 つに等しい。**

開けっ放しにしないのは、**これが誰でも叩けてメールを出す口**だからで、いま入る人が
1 人しかいない以上、世界中に開ける理由が無い。

**応答は許可の有無で変えない。** 送っても送らなくても同じ返事にする。区別すると、
誰がこのサイトに入れるのかを総当たりで数えられる。

### 連打は 2 段で止める

- `ratelimits` バインディング (IP 単位)。**この口が使えるのは 10 秒か 60 秒の窓だけ**
  なので、担えるのは瞬間的な連打まで
- 生きているトークンの本数でアドレス単位の上限を持つ。窓は寿命の 15 分と同じで、
  **受信箱を埋めさせない**のがこちらの役目。送り直しは効く

## 帰結 / Consequences

- 良い面: 預かる秘密が無い。事前に許可を置ける。端末をまたげる。管理者と読み手で
  仕組みが 1 つ。passkey を足すときも、アドレスに紐づく資格情報が 1 種類増えるだけ
- 悪い面・トレードオフ:
  - **メールの到達と遅延に乗る。** 届かなければ入れない。送信元ドメインの評判を
    保ち続ける必要がある
  - **別の端末では確認を 1 回押す。** 踏めばそのまま入れる形より手数が 1 つ多い
  - **メールを乗っ取られたら終わり。** 管理者も同じなので、ここが単一障害点になる。
    passkey を別に維持する額には見合わないと判断した (#480)
  - `ADMIN_EMAIL` を置き忘れた環境では**誰も入れない**。黙って全員を通すよりよい
    (secure by default) が、設定の抜けは 401 としてしか見えない
- 検証方法 / 今後の宣言:
  - `GET /sign-in/callback` が**トークンを消費しないこと**をテストで固定する。
    ここが崩れると、リンク検査に潰される形に戻る
  - 応答が許可の有無で変わらないことをテストで固定する
  - `POST` が `Origin` の違う要求を落とすことをテストで固定する
