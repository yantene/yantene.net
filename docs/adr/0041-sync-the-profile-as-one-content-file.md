# 0041. プロフィールはコンテンツのファイル 1 つとして同期し、経歴は本文に持つ

- Status: Accepted
- Date: 2026-09-15
- Deciders: @yantene

## Context / 背景

`/about` に出す書き手のプロフィールが要る。名前・短い自己紹介・生年月日・出身地・
出ていく先と、これまでやってきたこと (経歴) と、好きなもの。

置き場はコンテンツリポジトリで決まっている。発信の中身はすべてあちらが持ち、コードは
扱い方だけを持つ ([0034](0034-artifacts-as-content-source-of-truth.md))。プロフィールも
発信の中身なので、コードに直書きすると書き換えるたびにデプロイが要る。

決める必要があるのは**経歴をどう持つか**である。経歴は「いつ・何があったか」の並びなので、
構造として持てば並べ替えも、粒度ごとの表示 (「1993 年 11 月 18 日」「2012 年 4 月」) も、
別の画面からの参照もできる。年別のアーカイブに学年を注釈する構想 (#414) は、
まさにその構造を欲しがる。

## 検討した選択肢

- **案 A: 経歴をフロントマターの構造として持つ** — `lifeEvents` に `date` / `kind` /
  `title` / `description` を並べ、D1 の別表に入れる。
  - Pros: 並べ替え・絞り込み・他の画面からの参照ができる。日付の粒度を型として持てる
  - Cons: 日付の粒度が 3 通り (`1993-11-18` / `2012-04` / `2012`) になり、YAML の型解釈
    (年だけは数値で返る) に依存した読み取りが要る。項目が増えるたびに欄と表と検証が増える。
    「Ruby 合宿 2012 春」のように日付に収まらない出来事を書けない
- **案 B: 経歴を本文の Markdown に書く** — `## History` の下に箇条書きで並べ、本文ごと
  MDAST にして R2 に置く。
  - Pros: 書き手が文章として書ける。リンクも注釈も入れ子も、記事と同じ書き方でそのまま
    通る。同期は 1 ファイルの読み取りで済む
  - Cons: 機械が「いつ何があったか」を読めない。#414 が要るときは作り直しになる

## 決定

**案 B を採る。** プロフィールはコンテンツリポジトリの `profile.md` 1 つで、
フロントマターが構造 (名前・生年月日・出身地・短い自己紹介・出ていく先) を持ち、
**経歴と好きなものは本文に置く**。

保存先は D1 の 1 行と R2 の MDAST 1 つ。

- D1 `profile` — `id = 1` に固定した 1 行。名前・生年月日・出身地・tagline・
  出ていく先 (JSON)・`source_hash`
- R2 `profile/mdast.json` — 本文の MDAST

構造で持つのは、**記事の末尾やトップのヒーローなど `/about` の外でも要るものだけ**にする。
経歴はいまのところ `/about` でしか読まれず、読まれ方も「上から順に読む」しかない。
構造にしても、いまは畳んで文章に戻すことしかしない。

同期は記事と同じ経路に相乗りする。`POST /api/v1/refresh` と push の Queue
([0035](0035-refresh-on-push-through-a-queue.md)) の両方から走り、変更検出も記事と同じ
ファイルハッシュで行う。Markdown を MDAST にする経路 (Alert・文中の改行の畳み込み・
数式) は記事と共有する (`services/markdown-document.ts`)。**本文の書き方は書いた場所で
変わらない**ので、経路を分けると片方だけ古びる。

## 帰結 / Consequences

- 良い面: 書き手は経歴を文章として書ける。日付に収まらない出来事も、リンクも、入れ子の
  箇条書きも書ける。同期・保存・描画のどれも記事の作りをそのまま使える
- 良い面: 欄が増えても D1 の列が増えるだけで、表は増えない
- 悪い面: 機械が経歴を読めない。#414 (年別アーカイブに学年を注釈する) をやるときは、
  そのときに要る構造だけを新しく決め直すことになる
- 悪い面: 出ていく先を JSON の列に畳んでいるので、SQL で絞り込めない。**引くのは
  `/about` の 1 か所だけ**なので、いまは困らない
- トレードオフ: **全件削除のガードを置かない。** 記事のほうがそれを要るのは、閲覧数と
  届いた Webmention がコンテンツリポジトリのどこにも無く、消したら戻せないため
  ([0040](0040-article-status-and-reader-facing-repository.md))。プロフィールが持つのは
  `profile.md` に書いてあることだけなので、間違って消しても push し直せば元に戻る
- トレードオフ: **`status` を持たない。** 置いてあるものはそのまま読み手に出る。隠したい
  版は push しなければよく、段階を分ける実益が無い (記事と違って 1 つしか無い)
- 検証方法: `services/profile-refresh.service.test.ts` が同期と、読めないフロントマターの
  扱いを固定する。`handlers/profile/about-page.handler.test.ts` が「D1 の行はあるのに
  R2 の本文が無い」ときに「準備中」へ倒すことを固定する。`routes/about.test.tsx` が
  2 通りの描かれ方を、`components/profile/profile-card.mf2.test.tsx` が microformats の
  印を固定する

### 中身が無いときは「準備中」に倒す

初回の refresh の前と、`profile.md` を消した直後は D1 に行が無い。**そこで 500 を出さない。**
ヘッダーのナビは常に About を指しているので、行き先が落ちるとサイトが壊れて見える。

`noindex` を立てるのも、sitemap から外すのも、このときだけ。**3 つは必ず一緒に動かす**
(`routes/about.tsx` / `handlers/seo.handler.ts` / `scripts/smoke.mjs`)。

### 代表 h-card はトップのまま

`/about` にも `h-card` を置くが、これは同じ人を指す**別の** h-card である。Bridgy Fed が
「誰のサイトか」を読む代表 h-card はトップのヒーローにあり、動かさない。代表が 2 つあると、
どちらを読むかが決まらなくなる。

そのため `/about` の `u-url` は、このページ自身ではなく出ていく先に付けてある。
