# 0051. 作品にスクリーンショットと関連記事を持たせ、記事は描画のたびに引き直す

- Status: Accepted
- Date: 2026-11-16
- Deciders: @yantene

## Context / 背景

作品 ([ADR 0042](0042-keep-works-as-their-own-content-kind.md)) が持つのは名前・概要・在り処と
本文だけで、`/works/<slug>` を開いても字しか出ない。どんなものかは画面を見れば早く分かるのに、
見せる場所が無い。作品について書いた記事があっても、作品のページからは辿れない。

制約が 3 つある。

- **書き手の手間を増やさない。** 既に置いてある作品が、何も書き足さなくても今どおりに出る
  こと。
- **隠した記事を漏らさない。** 記事は段階 (`status`) を持ち、下書きに戻すこともある
  ([ADR 0040](0040-article-status-and-reader-facing-repository.md))。作品から記事を指す線が、
  その隠し方を迂回してはいけない。
- **同期の順番に意味を持たせない。** 作品と記事は同じ push で届くが、どちらが先に D1 に
  入るかは実装の都合でしかない。

## 検討した選択肢

関連記事をいつ解決するか。

- **案 A: 同期のときに解決して、記事の id で持つ** — `work_articles (work_id, article_id)`。
  - Pros: 外部キーが張れる。描画は結合 1 つで済む。
  - Cons: 記事がまだ無いと入れられないので、作品より後に同期される記事を指せない。
    「同期のとき公開されていた」ことを覚えてしまうので、あとで記事を下書きに戻しても
    作品のページに残る。
- **案 B: 記事の側に書く** — 記事のフロントマターに `works: [<slug>]`。
  - Pros: 記事の段階と一緒に動く。
  - Cons: 作品のページでの並びを書き手が決められない。両方に書けるようにすると
    二重に持つことになり、どちらかが古びる。
- **案 C: 作品の側に slug で書き、描画のたびに引き直す** — `work_articles (work_id,
article_slug, position)`。

スクリーンショットをどこに書くか。

- **案 D: 本文の先頭に画像として貼る** — 今ある仕組みだけで済む。
  - Cons: 一覧のカードと OG 画像が「1 枚目」を引けない。枠の比率 (横長か縦長か) を
    書く場所が無い。
- **案 E: フロントマターに並びとして持つ** — `screenshots: [{ src, alt, kind? }]`。

## 決定

**案 C と案 E を採る。** 足した欄はどれも省略でき、書いていない作品は今どおりに出る。

| 欄            | 中身                                  | 置き場                         |
| ------------- | ------------------------------------- | ------------------------------ |
| `featured`    | `/works` で大きく出すか。真偽値だけ   | `works.featured`               |
| `stack`       | 使った技術の名前の並び                | `works.stack` (JSON の配列)    |
| `period`      | 作った時期。`from` と、任意の `until` | `works.period_from` / `_until` |
| `role`        | 自分の役割 (1 行)                     | `works.role`                   |
| `screenshots` | 画面。`src` / `alt` / `kind`          | `work_screenshots`             |
| `articles`    | この作品について書いた記事の slug     | `work_articles`                |

### 関連記事は slug で持ち、描画のたびに読み手向けの読み口で引く

`work_articles` が持つのは記事の id ではなく slug で、`articles` への外部キーは張らない。
**読み手に見せてよいかは保存のときに決めない。** `/works/<slug>` を描くたびに
`D1ArticleQueryRepository.forReaders(d1).findBySlugs` で引き直し、`published` の記事だけを
書き手が並べた順に出す。下書き・限定公開・取り下げ・まだ無い記事は黙って外れる。

- **限定公開 (`unlisted`) も外す。** URL を知っていれば読める記事だが、作品のページに
  並べた時点で「一覧に出ない」が破れる。だから `findBySlug` (限定公開も通す) は回さない
- **管理者でも `forReaders`。** ここは slug で 1 本引く経路ではなく記事を並べる経路
  (ADR 0040)
- **関連記事の slug そのものを応答に載せない。** `PublicWork` には入れていない。slug だけ
  でも、書きかけの記事が在ることが漏れる。「関連記事 N 本」のような数も、引き直したあとの
  並びから数える

**知らない slug を書いても作品は同期する。** 同期の結果の `works.warnings` に出すだけ。
スキップにすると、作品と記事のどちらが先に入るかで結果が変わる。警告は**保存されている
全作品について毎回**出す (読み直した作品だけに出すと、次の push で消えて、直っていない
誤りが直ったように見える)。slug として読めない字 (`Why I Built It`) は、この先どの記事とも
一致しないのでスキップにする。

### スクリーンショットは同期のときに確かめ、割れた絵を見せ場に出さない

`src` は `works/<slug>/` に置いた画像への相対パスで、同期がアセット API の URL
(`/api/v1/works/<slug>/assets/<path>`) に解決し、寸法を画像のヘッダーから読んで添える
(本文の画像と同じ処理)。

**1 つでも次に当たれば、作品ごとスキップして前の姿を残す。**

- `alt` が無い。スクリーンショットは飾りではなく中身なので、字でも持つ
- `src` がその作品の置き場に実在しない。打ち間違い、外の URL、`../` がここに入る
- `src` が `_` で始まる要素を含むパスを指している。そういうパスは同期で落とすので
  ([#559](https://github.com/yantene/yantene.net/issues/559))、R2 に写らず配れない。
  下書きの置き場を見せ場から指させない

確かめるのは R2 に書き始める前。書いたあとで引き返すと、R2 だけが新しい姿になる。

寸法を読めなかった画像 (判別できない形式) はスキップにせず、寸法を持たないまま通す。
枠の大きさは `kind` の比率のクラスと CSS の高さで決まり、画像の寸法には頼っていないので、
読み込みの前後でページは動かない。

### 書き込みは 1 つの batch

作品の行・スクリーンショット・関連記事を 1 つの `db.batch` で書く。子の行は差分を取らず、
消してから入れ直す。途中で落ちても「名前は新しいのにスクリーンショットは前のまま」は
表に出ない (プロフィールと経歴の書き込みと同じ考え方。
[ADR 0041](0041-keep-the-profile-in-the-content-repository.md))。

### 時期は経歴の日付をそのまま使い、並びには使わない

`period` の日は経歴の `HistoryDate` (3 段の精度) で、終わりの決まり (同じ精度で、
始まりより後) も同じ関数が見る。**並びは今も `position` だけが決める。** 日付を持ったから
といって作った順に並べると、一覧が年表になる (ADR 0042)。

## 帰結 / Consequences

- 良い面: 記事の段階を変えれば、作品のページもそれに従う。作品を同期し直す必要が無い。
  記事を後から書いても、公開した時点で作品のページに並ぶ。
- 良い面: 作品と記事の同期の順番に意味が無い。
- 悪い面: `/works/<slug>` を開くたびに記事を引く問い合わせが 1 つ増える (関連記事を
  書いた作品だけ)。
- 悪い面: 1 作品に書ける数に上限がある (スクリーンショット 12 枚、関連記事 30 本)。
  関連記事は slug を `IN (...)` に並べて引くので、D1 のバインドパラメータ上限 (100) を
  超えるとページが 500 になり、しかも手元 (node:sqlite) では踏めない。
- 悪い面: スクリーンショットは古びる。作品の見た目が変わっても撮り直さなければ、昔の
  画面が出続ける。
- トレードオフ: `works/` の書式の誤りは push の前には分からない (`scripts/check-publish` が
  読むのは `articles/` だけ)。同期の結果の `skipped` と `warnings` で気づく。push で走る
  同期の結果は Workers Logs に出る。
- 検証方法: `pages.handler.test.ts` が、読み手に見えない記事 (下書き・限定公開・取り下げ・
  まだ無い記事) の slug が応答のどこにも (JSON-LD にも、一覧にも) 残らないことを固定する。
  `works-refresh.service.test.ts` が、置き場に無い `src` と `_` で始まる `src` で作品が
  スキップされ R2 が書き換わらないこと、知らない slug が警告に留まることを固定する。
  `work.repository.test.ts` が 1 文あたりのバインドパラメータ数を schema から数えて見張る。
