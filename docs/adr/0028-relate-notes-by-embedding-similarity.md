# 0028. 関連ノートを、refresh 時に作るベクトルの近さで並べる

- Status: Proposed
- Date: 2026-09-01
- Deciders: @yantene

## Context / 背景

記事ページの関連ノートは、共通するタグの数で並べていた
(`note.query-repository.ts` の `findRelated`)。並びは共通タグ数の降順、公開日の降順、
slug の昇順である。

正本の 57 本を数えると、この第 1 キーがほとんど働いていない。タグは延べ 116 個・19 種類で、
1 記事にしか付いていないタグが 8 種類ある。1 記事あたりのタグ数は 1 個が 16 本、2 個が 27 本で、
半数以上が 2 個以下に収まる。しかも 34 本に「日記」が付いている。

その結果、候補になる記事の共通タグ数はほとんど 1 に潰れ、並び順を決めるのは第 2 キーの
公開日になる。実際、直近 3 本のうち 1 本 (`claude-code-anywhere-with-devpod`) は付けた
5 個のタグがどれもその記事にしか付いておらず、関連ノートが 0 件になる。残る 2 本は
2013 年前後の記事が公開日降順で並ぶ。

タグを丁寧に付けるほどその記事だけのタグが増えて 0 件に近づき、雑に付けると「日記」に
吸われて公開日順になる。どちらに転んでも共通タグ数は仕事をしていない。

## 検討した選択肢

- **案 A: TF-IDF とコサイン類似度** — 本文の語の重みからベクトルを組み、近い順に並べる。
  - Pros: 外部サービスに触らない。なぜ関連なのかを共通の語で説明できる。関連記事という
    機能の教科書解で、40 年の実績がある。`Intl.Segmenter` が V8 に入っているので日本語の
    語の分割に辞書を持ち込まなくてよい
  - Cons: 語彙が一致しないと 0 になる。「競プロ」と「TopCoder」がつながらない
- **案 B: FTS5 の bm25 で More Like This** — 既にある `notes_fts` に本文を投げて上位を取る。
  - Pros: 新しいバインディングもテーブルも要らない。索引は既に D1 にある
  - Cons: 索引が trigram なので語の単位で重みを見ていない。特徴語を抜き出して投げ直す
    前処理が要る。語彙の一致に依存するのは案 A と同じ
- **案 C: 文書ベクトルとコサイン類似度 (採用)** — モデルに本文を渡してベクトルを作り、
  記事どうしの近さを計算する。
  - Pros: 語彙が違っても意味が近ければつながる。タグを人が付けなくてよい
  - Cons: 外部のモデルに触るので失敗する経路が増える。なぜ関連なのかを数値でしか
    説明できない
- **案 D: Vectorize に置く** — Cloudflare のベクトルデータベースに入れて近似最近傍で引く。
  - Pros: 記事数が増えても検索が速い
  - Cons: 57 本の全ペアは 1,596 通りしかなく、総当たりで足りる。1 ベクトル 1536 次元までの
    制限があり、日本語向けの plamo-embedding-1b (2048 次元) が入らない

## 決定

案 C を採る。ベクトルは refresh のときに作り、D1 に置く。

置き場は 2 つの表に分ける。

- `note_embeddings` — 記事 1 本ぶんのベクトル。作ったモデルと、作った時点の
  `source_hash` を一緒に持つ。本文が変わったときとモデルを差し替えたときに作り直す
- `note_similarities` — 記事どうしの近さ。**上位 N 件に切り詰めず、ペアのまま置く**

ベクトルは生成した時点で L2 正規化して持つ。コサイン類似度が内積だけになり、正規化を
後段に任せたときに起きる「片方だけ正規化された行が混ざる」事故が起きない。

Vectorize は使わない (案 D)。近似最近傍が要る規模ではなく、使わないことでモデルの
選択肢が次元数で狭まらずに済む。

計算と保存は `NoteEmbeddingsRefreshService` が担い、ノートの同期
(`NotesRefreshService`) からは分ける。外部のモデルに触るので失敗の扱いが違い、
リンクカード (ADR 0014) と同じ理由で別のサービスにしている。ベクトルを作れなかった
記事は、前回のベクトルと近さがそのまま残る。

## 帰結 / Consequences

- 良い面: タグを人が付けなくても関連ノートが並ぶ。タグが 1 個しか付いていない記事でも、
  その記事だけのタグしか無い記事でも、0 件にならない
- 良い面: 読み手のリクエストは D1 を 1 回引くだけで、外部に触らない。タグ版と同じ形である
- 悪い面: なぜこの記事が関連なのかを、読者にも書き手にも説明できない。タグ版は
  「共通タグ: GNU/Linux」と出せた
- 悪い面: `note_similarities` は記事数の 2 乗で増える。両方向で持つので 57 本で 3,192 行、
  1,000 本で 999,000 行 (約 38 MB)。D1 の上限 (有料 10 GB / 無料 500 MB) に当たるのは
  数千本のあたりで、そこまで来たら上位 N 件に切る形へ移すことになる
- トレードオフ: 上位 N 件を保存せずペアのまま置くのは、refresh が変更のあった記事しか
  処理しないため。切って保存すると、後から書いた記事が古い記事の関連ノートに永久に
  出てこない。行数と引き換えに、その穴を塞いでいる
- 検証方法: `embedding-vector.vo.test.ts` が正規化と内積、保存形式の往復、次元違いの
  拒否を固定する。`note-embeddings-refresh.service.test.ts` が、本文もモデルも変わって
  いない記事を作り直さないこと、同じ回に処理した記事どうしがペアになること、モデルが
  落ちても記事の同期を止めないことを固定する
