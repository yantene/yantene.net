# 0031. 埋め込みの入力の上限を 8,000 字から 10,000 字に上げる

- Status: Accepted
- Date: 2026-09-09
- Deciders: @yantene

## Context / 背景

[ADR 0030](0030-switch-embedding-model-to-qwen3.md) は `MAX_INPUT_CHARACTERS` を 8,000 字のまま残した。
根拠は、ASCII が半分混じるいちばん長い記事を繰り返した文章で、`qwen3-embedding-0.6b` のベクトルが
変わらなくなる (8,192 トークンから先を黙って切り捨てる) 長さが 16,000 字と 24,000 字の間だったことと、
日本語だけの散文はもっと短いはずだという見込みである。見込みの部分を測っていなかった。

記事「Workers AI で「関連ノート」機能を作り直した。タグは廃止した。」の推敲で、
「8,000 字は余裕を持ちすぎではないか」という読者の反論を置くことになり、2 つの方法で測った。

- Qwen3-Embedding-0.6B の tokenizer (Hugging Face の `tokenizer.json`) で 55 本を数えると、1 トークンあたり
  1.39 字から 2.13 字、中央値 1.65 字。ASCII が少ない日本語の散文ほど密で、最も密なのは JOI 予選の失敗記
  (1.39 字)。同じ方法で `bge-m3` の tokenizer を使って実験の 24,000 字を数えると 11128 トークンになり、
  ADR 0030 のエラーメッセージ「Sequence too long: 11128 > 8192」と一致した
- 実験用の Worker から、最も密な JOI のノートと日本語だけの散文 (乾燥機のノート) を繰り返した文章を
  500 字刻みで 16,000 字まで投げ、ベクトルが変わらなくなる長さを 4 モデルで測り直した
  (`tmp/embedding-experiment/src/probe-dense-limit.py` → `data/dense-limit.json`)

| モデル                 | JOI のノート (最も密)                     | 乾燥機のノート (散文)     | ADR 0030 の実測 (ASCII 半分) |
| ---------------------- | ----------------------------------------- | ------------------------- | ---------------------------- |
| `bge-m3`               | 13,500〜14,000 字でエラー (8378 トークン) | 13,500〜14,000 字でエラー | 24,000 字でエラー            |
| `qwen3-embedding-0.6b` | 11,500〜12,000 字                         | 12,500〜13,000 字         | 16,000〜24,000 字            |
| `plamo-embedding-1b`   | 6,000〜6,500 字                           | 6,500〜7,000 字           | 8,000〜10,000 字             |
| `embeddinggemma-300m`  | 3,500〜4,000 字                           | 4,000〜4,500 字           | 5,000〜6,000 字              |

tokenizer から見積もった qwen3 の 11,400 字 (8,192 × 1.39) と、実測の 11,500〜12,000 字が合う。
8,000 字は、最も密な比率でも約 5,800 トークンで、8,192 の 7 割にあたる。

## 検討した選択肢

- **案 A: 8,000 字のまま** — 切り捨てはエラーにもログにも出ないので、余裕を厚く取る。
  - Cons: 密な記事でも 11,500 字まで入ると分かったうえで 7 割に置く理由が無い。10,000 字の記事が
    2 つに割られて平均になる
- **案 B: 10,000 字 (採用)** — 密なほうの実測の下端 11,500 字に 0.85 を掛けて千字単位に丸めた値。
  - Pros: 最も密な記事でも約 7,200 トークンで上限に届かない。8,000 字を超え 10,000 字に収まる記事を
    分割せずに読める
  - Cons: 55 本より密な記事 (1 トークンあたり 1.22 字を切るもの) が来ると後半が消える。ASCII の
    少ない漢字だらけの文章はそちら側に寄る
- **案 C: 11,000 字** — 実測の下端ぎりぎり。
  - Cons: 500 字刻みの実測なので下端そのものに誤差がある。切り捨てが見えない以上、ぎりぎりに置く
    ものではない

## 決定

案 B を採る。`MAX_INPUT_CHARACTERS` を 10,000 にする。

上限の置き方を規則にして、実験 (`tmp/embedding-experiment/src/embed.ts`) の 4 モデルにも同じ規則を使う。
「密な日本語で測った上限の下端に 0.85 を掛け、千字単位に丸める」で、`qwen3-embedding-0.6b` 10,000 字、
`plamo-embedding-1b` 5,000 字、`embeddinggemma-300m` 3,000 字、`bge-m3` 11,000 字。ADR 0030 までの実験は
モデルカードのトークン数 × 0.73 で置いた 24,000 / 3,000 / 1,500 / 8,000 字で回していて、qwen3 の 24,000 は
誤っていたモデルカードの 32K から出た数だった。

## 帰結 / Consequences

- 良い面: 8,000 字を超え 10,000 字までの記事を分割せずに読む。実験の分割は `plamo-embedding-1b` が
  8 本から 3 本、`embeddinggemma-300m` が 16 本から 8 本に減り、タグを物差しにした指標は
  `embeddinggemma-300m` の AUC が 0.829 から 0.820、日記以外のタグ共有率が 57.0% から 54.5% に下がった。
  順位 (gemma > plamo ≒ qwen3 > bge-m3) は変わらない
- 悪い面: 切り捨てが見えないのは変わらない。密な記事の後半が消えても、関連ノートがおかしいと気づく
  まで分からない
- 検証方法: 上限を動かすときは `probe-dense-limit.py` を回し直し、密なほうの下端 × 0.85 を守る。
  本文が 10,000 字を超える記事を書いたら、refresh の結果でチャンク数が 2 になることを確かめる
