# 0042. 作ったものを独立した種別として持ち、`/works` で配る

- Status: Accepted
- Date: 2026-09-14
- Deciders: @yantene

## Context / 背景

`/about` の長い自己紹介に「作っているもの」の節があり、作品の名前とリンクが散文の中に
並んでいた。増えるたびに本文を書き直すことになり、機械からは名前も在り処も読めない。

一方で、自己紹介を読みに来た人がいちばん見たいのは「この人は何を作ったのか」であることが
多い。散文に埋めておくと、拾うのに全文を読ませることになる。

制約が 2 つある。

- **年表にしない。** 同じ `/about` に置いていたライフイベントのタイムラインを、
  「読み手が最初に受け取るのが履歴書になる」という理由で落としたばかり
  ([ADR 0041](0041-keep-the-profile-in-the-content-repository.md))。作った順に並べる
  一覧は、名前を変えて同じものを戻すことになる。
- **`visibility` を増やさない。** 公開範囲の欄は `status` への改名が進行中で、写すと
  もう 1 本 migration と改名が要る。

## 検討した選択肢

- **案 A: `/about` の散文のまま置く** — いまの姿。
  - Pros: 何も作らなくてよい。書き手は文章を書くだけで済む。
  - Cons: 増えるたびに本文を書き直す。機械から読めない。作品ごとの行き先が無いので、
    詳しく書きたくなったときの置き場が無い。
- **案 B: プロフィールのフロントマターに一覧を持つ** — `profile.md` に `works:` の並びを
  足し、`profile_works` の子表に入れる。
  - Pros: 表が増えない。同期の経路も 1 つで済む。
  - Cons: 作品が自己紹介の一部になる。詳しい説明を書く場所が無く、`/works/<slug>` を
    後から生やすなら結局コンテンツを分けることになる。
- **案 C: 記事の一種として書く** — `articles/<slug>.md` に書き、何かの印で作品だと示す。
  - Pros: 同期も配信も既にある。
  - Cons: フィードに流れる。作品は「更新のお知らせ」ではないので、購読している人に
    書き直すたび届く。一覧に混ざって時系列に並ぶのも、作品の並べ方としては違う。
- **案 D: 独立した種別にする** — `works/<slug>.md` を記事と並ぶ種別として扱う。

## 決定

**案 D を採る。** `content/works/<slug>.md` + `content/works/<slug>/<asset>` を、記事と
同じ経路 (push → Queue → refresh → D1 + R2) で同期する。

出る場所は 3 つ。同じ 1 つのデータから賄う。

| 場所            | 出すもの                                 |
| --------------- | ---------------------------------------- |
| `/about`        | 名前・概要・在り処 (フロントマターまで)  |
| `/works`        | 同じ一覧に、この場所の名乗りを添えたもの |
| `/works/<slug>` | 詳しい説明 (本文の MDAST)                |

記事との違いを 4 つ決める。

**並びは `position` で持つ。日付では並べない。** 作った順に並べると年表になる。何をいちばん
見てほしいかは書き手が決めることなので、フロントマターに書いた数で決める。省略は許さない
(既定値を置くと、書き忘れた作品がどこに挟まるかを書き手が決められなくなる)。同じ数を
2 つ書いたときは slug で決める — 誤りではあるが、refresh のたびに順が入れ替わるより、
決まった順で出続けるほうが気づきやすい。

**公開範囲は持たない。** 出したくないものは push しなければよい。数件を手で選んで置く
ものに、配信側で隠す仕組みは要らない。

**フィードは作らない。** 作ったものは購読するものではない。時系列に増えないので、
購読先を実在させても何も届かない。[ADR 0038](0038-split-feeds-by-content-kind.md) が
「中身の無い種別も購読先として実在させる」と決めているのは、いずれ時系列に増える種別
(Notes / Slides) の話で、ここには当てはまらない。**それでもナビには出す** — ナビは
「この場所には何があるか」を示すもので、購読の口があるかとは別。

**検索の索引と埋め込みを作らない。** 探して辿り着くものではないし、本文どうしの近さを
測っても意味のある並びにならない。

`/about` は**全件**を出す。「代表の N 件」に切ると順位の定義が要るが、`position` が既に
その役を果たしている。切らないので「すべて見る」の導線も置かない (出ているのが全部なので、
続きがあると言うことになる)。行き先としての `/works` は節の見出し自身が持つ。

## 帰結 / Consequences

- 良い面: 作品が増えても本文を書き直さない。名前・概要・在り処が機械から読める
  (`CreativeWork` の JSON-LD を出す)。詳しく書きたくなったら本文に書けばよく、置き場を
  後から探さずに済む。
- 良い面: 年表にならない。`/about` に並ぶのは「何を作ったか」であって「いつ作ったか」
  ではない。
- 悪い面: `/about` と `/works` が同じ一覧を出す。作品が数件のうちは `/works` の存在意義が
  薄い。それでも独立したページを置くのは、`/works/<slug>` に親が要ることと、ナビの
  行き先が必要なため。
- 悪い面: 表が 1 つ (`works`) と migration が 1 本増える。R2 のキーも `works/` が増える。
- トレードオフ: `WorkSlug` は `ArticleSlug` の規則を写している。共通化しなかったのは
  `article-slug.vo.ts` を触る範囲を広げないためで、片方だけ規則が動く余地は残る。
  読めなかったときに undefined を返す作法 (`parse`) は必ず両方で守ること — ここが崩れて
  #291 になった。
- 検証方法: `works-refresh.service.test.ts` が同期の不変条件 (変更が無ければ読まない /
  誤字では前の姿を残す / 消えたら掃除する / ツリーが空なら掃除を拒む / infra 障害は投げる)
  を固定する。`work.repository.test.ts` が並び順と同値の決着を固定する。
  `feed-menu.test.tsx` が「時系列の行き先とフィードは 1 対 1」を見張り、`/works` が
  そこに入っていないことを含めて固定する。
